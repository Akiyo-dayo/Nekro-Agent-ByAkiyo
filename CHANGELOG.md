# Changelog

Version numbers here are this derivative edition's own (`FORK_VERSION` in `nekro_agent/tools/common_util.py`). This edition is based on upstream
NekroAgent `2.4.0` (`UPSTREAM_BASE_VERSION`; up to v0.4.2 it was based on `2.3.3`). The `version` in `pyproject.toml` is the plugin-compatibility version (`2.4.0`): plugins written for that
upstream version install and run here. It drives plugin-compatibility checks and update checks, and is not this edition's own version.
## v0.4.6 (2026-11-21)

Long-term memory no longer needs a CC workspace (off by default) and has a management page with per-round prompt details. New: worldbooks, SillyTavern character card compatibility, affection linked to memory, per-chat daily quotas, ops tools the agent can call, message recall, an output filter, an SSH gateway (off by default), and this edition's own CC sandbox image. Mailboxes and sticker libraries now belong to instances. Festival greetings no longer go to dead chats, and a chat the bot was removed from is disabled (and re-enabled) automatically. A long run of cross-tenant and host-side hardening: CC workspace container lifecycle, files read from directories that containers can write, per-instance plugin settings, invalid settings values no longer stopping start-up, and a memory scheduler that no longer stalls. Fourteen database migrations run on start-up. Two dependencies are added for installs from source: `regex` (already installed as a dependency of `tiktoken`) and `asyncssh` (used by the SSH gateway); the Docker images include both. Read the upgrade notes before switching.

Published on 2026-11-21 together with v0.4.5 and v0.4.7: the public edition had not been updated since v0.4.4. Coming from v0.4.4, go straight to v0.4.7 and read the upgrade notes of all three versions.

### Fixed
- Tenant admins can no longer read the SSH gateway settings (`SSH_GATEWAY_*`), which include the allowlists of who may trigger and register servers; like the ops bot settings, they are now visible and editable only on the platform side.
- One invalid value in a settings file no longer stops the app from starting. A value out of range is clamped to the nearest allowed value, a value of the wrong type goes back to the default (in an instance or chat override, or in a plugin's per-instance settings, it goes back to the value from the level above instead), and the other settings in the file load as written; each repair is logged as an error naming the file, the setting, the old and the new value. If the main settings file needed repairs, the original is first saved next to it as `nekro-agent.yaml.pre-repair-<time>`, readable only by the owner, and the log names that file; it may contain credentials, so delete it once you have checked it. This applies to the main settings file, instance and chat override files, adapter settings and plugin settings (including a plugin's per-instance settings, which used to fall back to the global values as a whole). Saving an out-of-range value in the console is now refused with a message giving the allowed range, instead of being written to the file; a batch of changes is saved all or nothing. The `conf_set` chat command applies the same checks, and setting a boolean to `false` with it now works.
- Worldbook: a few blocked replies in a row no longer quarantine all of a book's constant entries at once. Constant entries are injected in every round, so they used to reach the quarantine threshold together and the persona's setting disappeared. They are now only counted, never quarantined automatically, and a blocked round that used more than 5 keyword entries is only counted as well. The reason on the quarantine tab now says how many blocked rounds led to an automatic quarantine.
- Long-term memory now refers to the bot by the name of the persona it is using in that chat. Before, it often wrote "Assistant" (for example "Assistant (playing the role of …)" in the memory graph). Arrangements that someone proposed and the bot agreed to are no longer marked as the bot's own words, and relationship milestones refer to the person by the name the bot calls them. Memories written before this version keep their wording.
- CC workspaces: restarting a workspace container could let the code running in it get a directory of the host mounted read-write into the container (it could replace `.claude_home` with a symbolic link just before the restart, and Docker follows such links). Containers are now stopped before their mounts are repaired and checked, mount sources are used as they are on disk, and a container is not started when a mount source is not a plain directory (the error is logged).
- Space cleanup no longer deletes files elsewhere on the host when a sandbox replaces one of its directories with a symbolic link between listing and deleting; such files are skipped.
- Files read from directories that containers can write to now have size limits (also while being read), and walking such directories has a depth limit, so a huge sparse file or a very deep tree can no longer exhaust memory or disk or crash the walk.
- Files in a sandbox's shared directory are now always opened without following symbolic links, also when NA's working directory path contains a symbolic link.
- CC workspaces: other containers of the same workspace (left by two starts at the same time, by an earlier start that timed out, or by a rebuild that could not delete the old container) could still swap `.claude_home` for a symbolic link after the checks above, and shared the workspace's API token. Starting, restarting, rebuilding and stopping a workspace are now done one at a time (a second start is refused as busy; a stop waits its turn, shown as "Starting/stopping"), every container of the workspace other than the one being started is stopped and deleted first (the start is refused if one cannot be), each new container gets its own API token, and leftover containers are deleted when NekroAgent starts. A restart, and NekroAgent's start-up, now check the mounts recorded in the container and stop it, asking for a rebuild, when it mounts anything other than its workspace, its `.claude_home` and a read-only `/etc/localtime` (a missing mount is fine, so containers from earlier versions keep running after an upgrade). Workspace containers run with `no-new-privileges` and without the `MKNOD` capability; containers created by earlier versions log a "rebuild recommended" warning on restart. A workspace is not started while another running container has a writable mount of the workspace or of any directory above it (NekroAgent itself and NapCat excepted), and deleting a workspace first stops anything from starting it again. Only single-process deployments are supported: several workers do not share the lock that keeps these operations in order.
- Host-side handling of directories that containers can write: deleting a very deep tree no longer fails (a tree too large to delete during start-up is moved aside and removed later), space statistics, cleanup and the memory tree no longer follow symbolic links and stop at a depth limit, files are checked to be regular files before they are really opened (and opening never waits on a file lease the container holds), files outside the sandbox's shared directory are only opened from the upload directory, and the workspace's API and relay tokens can no longer be put back to an old value by an unrelated settings save.
- Memory consolidation no longer stalls when many chats are active at once. Before, with a dozen busy group chats, the background scheduler could stop starting consolidations for a long time and quieter chats never got their turn. Each chat now has at most one place in the queue, waiting chats move up the longer they wait, and the scheduler logs the queue length and the longest wait at most once a minute. The setting "Stagger Delay" (`MEMORY_SCHEDULER_STAGGER_DELAY_SECONDS`) now means the minimum gap between two consolidation starts. Backlogs left by a restart now also drain on their own: after each batch the scheduler checks how many messages are still waiting in the database, keeps going while batches come back full, and at startup queues every chat with more than one batch waiting, even with "Recover Historical Consolidations On Startup" off.
- The backend test suite now exits on its own after printing its summary. Database connections that a test left open kept the process waiting at exit; they are now closed at the end of the test session.
- Code running in a CC workspace container or in the sandbox could place symbolic links in the directories it can write (the workspace, its `.claude_home`, the sandbox's shared directory), and NekroAgent then followed them when it wrote CLAUDE.md, `.mcp.json` and the settings files, synced skills, read or wrote knowledge-base files, wrote the sandbox's code files, or read files that plugins send to the chat. Depending on the place, that let the container read host files (for example the configuration file with the model keys) into the prompt, the console or the chat, write or delete files elsewhere on the host, make host directories world-writable, or get a host directory mounted into its next container. All of these now open paths level by level without following links: writes go to a temporary file renamed into place, reads accept only regular files, and deletions remove only the link. Downloading a file from a CC workspace into the sandbox is now limited to the workspace's working directory, excluding the configuration NekroAgent writes for CC, and the destination keeps only the file name.
- Pushes the host makes for plugins (festival greetings, timer reminders, the plugins' own background pushes and sends) now skip QQ groups that the periodic membership check has marked as "the bot is no longer in this group": no agent run is started and nothing is sent, so these groups no longer produce "removed from the group" errors and model calls for nothing. The chat is not disabled, and a new message from the group clears the mark as before. The festival greeting's summary log counts these groups separately.
- OneBot V11: notices that carry no group id (the protocol end's own status notices when it goes offline, friend-message recalls) are now skipped quietly instead of each producing an error with a traceback.
- OneBot V11: when the protocol end disconnects while a message or a group file upload is being processed, the event is dropped with one warning instead of an error with a traceback.
- In stream mode, the first-token timeout ("Stream First Token Timeout") now counts from when the request is sent. It used to start only after the model provider had sent its response headers, so a provider that held them back was given up on only after the full generation timeout (180 seconds by default). The descriptions of "Enable Stream Mode" and "Stream First Token Timeout" now say how they actually behave: token counts in stream mode are accurate when the provider supports `stream_options.include_usage` and recorded as 0 when it does not, and the first-token timeout is met by any chunk, empty ones included.
- Collecting a sticker from a link now goes through the same download guard as other downloads: addresses on the local or private network are refused (checked by the address the name resolves to, including after redirects) and images over 10 MB are rejected. Before, the sticker plugin fetched any link the model gave it.
- Permanently deleting a bot instance now also deletes the affection data that belonged only to that instance. Before, a new instance that later got the same name (possibly for another tenant) could read the old impressions and history.
- Relationship milestones: changes made by an admin (manual adjustments, resets, account merges) are no longer recorded as milestones the next time the bot updates its feelings, and an admin action that happens at the same moment as an update wins. When one instance of a shared group is moved to another tenant, its milestones are no longer shown to or changed by the original group. The bot's own adjustment no longer counts the same conversation twice when the background evaluation already did, and the check that keeps quotes out of the reasons looks at the whole visible conversation. The background evaluation's reasons and impressions now go through the same check: a reason or impression that repeats what someone said is replaced with a short note, and the score still counts.
- Affection page: editing the impression no longer overwrites a call name the bot changed in the meantime; the memory page can select everything matching a source filter in bulk; links between the affection and memory pages open in the right instance.
- CC model preset settings now reach Claude Code. Apart from the base URL, the token, the manual tier's model name and the timeout, a preset's settings (the preset tier's model such as `opus`, extra environment variables, the manual tier's small-fast model and model mappings) were written to a file outside Claude Code's working directory and never read, so Claude Code ran on its built-in default model. They are now written as Claude Code's user-level settings (`~/.claude/settings.json` in the workspace container), with the same rules as before for what a tenant workspace may receive. The old file is deleted on every settings write and on every start-up.
- Writing Claude Code settings into a workspace no longer follows symbolic links placed by the workspace container. The workspace directory is writable from inside the container, so code there could replace a settings file or its directory with a link and make NekroAgent write, delete or change permissions of a file elsewhere on the host. On Linux these writes now open every level of the path without following links, and a settings directory that has been replaced by a link is recreated as a real directory before the container is started.
- Worldbook import no longer truncates anything. Files up to 32 MiB with up to 50 000 entries, 1000 keywords per entry and long bodies and titles are imported in full; a file with an entry beyond these safety limits is rejected as a whole, with the entry and field named in the message. The import report points out entries whose body is longer than the per-round injection limit (`WORLDBOOK_MAX_CHARS`); they are still imported. Large books also import much faster.
- Worldbook matching is about four times faster when books have thousands of keywords; results are unchanged.
- Worldbook page: the trigger-test tab now uses the same card layout as the other tabs (and scrolls its tables sideways on narrow screens). The character-card import dialogs keep the frosted-glass look when full-screen, like the other dialogs.
- In a deployment with tenants, worldbooks the platform created for global presets are now visible to tenants read-only (marked "provided by the platform"), as long as the preset is visible to their instance: they can read the entries and see them in the trigger test and prompt preview, but cannot edit, delete, export or append to them.
- Routes that plugins add under `/plugins/<plugin>/` can now require the console login (with a short-lived ticket for live streams and images), and the built-in whiteboard's routes do: the whiteboard keeps one board per instance, a chat only changes and sees its own instance's board, and browser sources use a per-board read-only link that can be rotated. Old whiteboard URLs without board parameters now show a login prompt; copy the new read-only link from the demo page. Plugin settings can be marked platform-only or "tenants may only lower", and the mute report is only sent to a report chat in the same tenant.
- A plugin switched off for an instance or a chat now stays off in the background as well: message hooks, chat commands, timer reminders and the plugin's own pushes used to keep working there as long as the plugin was on globally or for any other instance (so switching off the cold-shoulder plugin did not stop it, and an instance switching on festival greetings greeted every group on the platform). Festival greetings now follow the global switch, then skip chats where the plugin is off; timer reminders of chats where the timer plugin is off are skipped. Plugins get push methods that check this first, and the built-in plugins use them. Dice predictions and the Google search throttle are kept per chat.
- In a deployment with tenants, CC workspaces that serve a tenant (or ever did) no longer receive the platform's credentials: with `NEKRO_CC_CREDENTIAL_MODE=direct` the real model key is not written into them and their CC answers that tenant workspaces need `relay`; workspace resources, global MCP entries with environment variables or headers, and preset environment variables that look like credentials are not handed to them either, and the workspace MCP endpoints no longer show those values to tenant admins. When a workspace becomes a tenant's, its running container is stopped if any of these had been handed to it, so they do not stay in its processes; for workspaces that were already running before the upgrade, the first start after upgrading works this out once from their configuration. A failure while preparing a CC call (for example a resource that cannot be decrypted) now ends with a redacted message on both the plugin and the admin "send to CC" path. See the new section "CC workspace model credential mode" in `docs/operations.md`; if a tenant workspace ever ran under `direct`, rotate the upstream key.
- In a deployment with tenants, the bots of tenant instances can no longer read the platform's mailboxes: the mail tools list only the platform's send-enabled mailboxes by display name (no address), and reading a mail, summarizing mail or forwarding an attachment is answered as if the mailbox did not exist. Sending mail is unchanged. The mail summary also no longer accepts a model group the chat's owner is not allowed to use, and the number of mails it reads is capped by the plugin setting. New-mail notifications are only pushed to a chat of the platform. The sticker plugin is paused for tenant instances until per-instance sticker sets arrive. Platform instances and single-tenant deployments behave as before.
- The built-in festival greeting no longer sends to every enabled chat blindly. Before each chat it skips chats whose bot instance is offline and, in blacklist mode, chats where nobody has spoken for a while (new setting "Skip Channels Inactive For (Days)", 30 by default, 0 turns it off). Before, a single festival could start an agent run in hundreds of dead chats, each of which failed to send.
- When the bot is kicked from or leaves a QQ group (OneBot V11), the chat is now disabled automatically instead of starting an agent run that cannot send anything, and the chat's detail page says why. It is re-enabled automatically, in its previous state, when the bot rejoins the group or the group speaks again. A chat you disabled by hand is never re-enabled automatically, and enabling or disabling a chat by hand ends the automatic handling for it.
- When a reply fails because the chat cannot be reached at all (the bot instance is offline, or the bot is no longer in the group), the bot no longer sends a failure notice into that chat, which would only fail the same way.
- OneBot V11 chats whose id does not end in a number (for example rows left behind by tests) now fail with an error that names the chat, instead of `invalid literal for int()`.
- A memory rebuild stopped as a whole when one chat hit a temporary provider failure. It now retries that batch a few times and, if it still fails, marks only that chat as failed and carries on with the others. The ops command `memory_rebuild <workspace_id> -y` never worked (it looked the workspace up as a job); it now starts the rebuild like the console does and reports the result, including failed chats. After a rebuild, live consolidation could process the just-rebuilt messages again and write duplicate memories; the chat's consolidation position is now moved past what the rebuild covered.
- The fallback model group for memory consolidation was only used after unparsable replies, so when the main group could not be reached (or timed out, or returned server errors), consolidation kept retrying the main group and backing off without ever trying the fallback. It now repeats the call once on the fallback group (if it differs from the main one) before recording a failure. Two consolidation log lines printed a literal `%s`; they show the actual values now.
- A failed memory consolidation run was counted as done, so the chat was only retried after enough new messages arrived. Failed runs now keep their pending messages and are retried on their own after a back-off; a chat that is backing off no longer delays the others. Embedding calls made for memory now record which instance they were for, so their usage can be attributed to the tenant.
- A deleted or quarantined memory could still be recalled into the prompt, and found by the memory tools, if updating the vector store failed at the moment it was deleted. Recall now also checks the memory's state in the database, so a leftover vector is never used.
- Reminders set through the timer plugin (or by other plugins through the timer API) put their description into a system message that triggered the agent, so a reminder worded by a chat member could later speak with the system's voice. Reminders, reminders re-sent after a restart and recurring reminders are now delivered as untrusted content under a fixed host summary, and still trigger the agent. The notice that a recurring reminder was paused after repeated failures is untrusted too, with credentials and internal addresses removed from the error text.
- Tenant accounts can now keep their own console language. Switching the language used to change the deployment-wide setting, which tenants may not change, so it always failed for them.
- Memory consolidation logs now tell apart a batch where the model found nothing worth keeping from one where its items were dropped as malformed: each batch logs one line with how many items the model returned, how many were kept and how many were dropped, and what happened to the channel summary.

### Changed
- CC workspaces use this edition's own cc-sandbox image by default: `ghcr.io/akiyo-dayo/nekro-cc-sandbox:0.1.14-ak3-cc2.1.311`, built from the public fork `Akiyo-dayo/nekro-cc-sandbox` (AGPL-3.0; the Python service is unchanged from upstream 0.1.14). Claude Code is pinned to 2.1.311 with its auto-updater off, Node.js is 22, the browser tooling and openssh-client / rsync / git are pinned, an SSH client config hook is added (`/etc/ssh/ssh_config.d/50-nekro.conf`), and tini runs as PID 1 so that force-cancelling a task no longer leaves zombie `claude` processes behind. Image tags never change and there is no `latest`.
- A workspace whose image version is `latest` (the stored default for workspaces that never set their own) now follows the global image tag instead of pulling `latest` literally, and saving a workspace's settings page no longer pins it to the image that happens to be the default at that moment. A workspace with its own image name still uses its version as written; clear the image name and version to make a workspace follow the default again.
- The sticker library is now per instance. Stickers are kept in sets: each instance has its own collection (what its bot collects goes there), and the platform owner keeps preset sets and assigns them to all instances, platform instances, one instance or one persona. A chat can use its instance's collection and the sets assigned to it or to its current persona (two new plugin settings narrow this down, but cannot add sets that are not assigned), and can change or delete only its own collection; platform sets are read-only for it. Each image is stored once by content hash, and collecting an image the chat can already see returns that sticker instead of overwriting someone else's. Collecting can be switched off per instance. The plugin also has the API for a sticker console (the page itself comes later), behind the console login.
- Mailboxes now belong to instances. The platform's mailboxes stay in the email adapter's settings; an instance can add its own (presets for common providers, including 126, Tencent Exmail and Aliyun; a custom server must resolve to a public address on a common mail port and is checked again before every connection; up to 3 per instance by default; an address can be configured only once across the platform). A chat on a tenant instance reads only its instance's own mailboxes and can send with them and with the platform mailboxes shared with that instance (new per-mailbox setting: all instances by default, listed instances, or none); it sees a shared mailbox only by display name. Sending mail now requires a reason, which is kept in a send log the admins can see. People can ask the bot to remember their own address and to subscribe to or unsubscribe from festival mail; only the one person speaking in that round can change their own settings. Festival greetings can also go out by mail, to people who private-chatted the instance or subscribed in a group, minus those who unsubscribed: the bot writes one greeting per instance (persona and festival only, no chat content, output filter applied) and a queue sends it evenly per sender mailbox, re-checking before each mail. An instance's own mailbox receives mail into the mail cache only, without creating an email chat, and can notify one chat of that instance. New admin API under `/api/instance-email/`, attachments by mail id, and "move to instance" / "back to platform" for mailboxes. A new "Mailbox" page under Chat Management manages an instance's own mailboxes, shows the platform mailboxes shared with it, and lists received mail, the send log, saved user preferences and festival mail. The sticker plugin serves its own console page (linked from the plugin detail page) for sorting stickers into sets and assigning sets. Mail servers entered by a tenant are checked again by the address actually connected to before the password is sent (host names must be ASCII; use the xn-- form for international domain names); changing a mailbox's provider or server requires entering its password again, and a mailbox's address cannot be changed (delete it and add it again). Those servers are dialled only at the address that passed the check (also for OAuth2 mailboxes and for a mailbox moved back to the platform, per server, until the platform changes that server), and addresses in the transparent-proxy Fake-IP range, or in extra networks the deployment allows for downloads, are not accepted for them. Status mail is not sent through a mailbox whose SMTP server was entered by a tenant; choose another sender. On a deployment behind a Fake-IP or TUN transparent proxy, mail servers entered by tenants cannot be made safe: turn instance mailboxes off there (see the operations guide). A new key file `email_account_ref.key` is created in the data directory; back it up with the rest of the data directory (the install scripts keep it readable by its owner only). Mail attachments in the console are loaded with the normal login header instead of putting the login token into the link. Moving a platform mailbox to an instance checks that the mailbox is still the one shown on the page. When an instance is moved to another tenant, its whiteboard's read-only link stops working, open whiteboard views of the previous owner are closed within half a minute, and the new owner starts with a blank board. Deleting a mailbox that was moved from the platform to an instance now also deletes the attachments of its mail, leaving other files in that folder alone.
- Plugin settings that belong to one instance or chat now follow the instance's lifecycle. Deleting an instance for good also deletes its plugin switches (on the instance and on its chats) and the plugin settings filled in just for it, such as API keys, so a new instance created later under the same key starts clean; if they cannot be deleted, the instance is not deleted either. Moving an instance to another tenant deletes them by default (the confirmation dialog shows how many plugins are affected and has a checkbox to keep them). Renaming a chat's key or migrating an instance's history moves them along, so per-chat switches are no longer lost. See section 1.8 of the operations guide.
- Settings changed just for one instance or chat (its own alert webhook, chosen model groups, prompts, output filter word lists and the like) follow the same rules as plugin settings: deleted with the instance, deleted by default when the instance moves to another tenant (with a checkbox to keep them), and moved along when a chat's key changes or an instance's history is migrated.
- Moving an instance's history to an instance of another tenant, or merging an unclaimed protocol endpoint into one, now deletes the source's plugin settings and per-instance settings by default; the confirmation shows how many there are and has checkboxes to keep them. When deletion is chosen nothing is carried over at all, including settings the previous owner writes while the move is running, and they are deleted from the source again afterwards. Moving an instance to another tenant also deletes them once more after the owner has changed. Deleting plugin settings is refused while another adapter has an instance with the same key, because both share them.
- Creating an instance first clears anything left behind under the same instance key, deleting an instance clears its settings once more after the database is updated (even if an earlier cleanup step failed), and the platform admin can no longer read or write plugin or per-instance settings for an instance or chat that does not exist. Folders that are symbolic links or junctions are no longer followed when an instance's settings or a mailbox's attachments are deleted. If clearing leftovers fails when a protocol endpoint registers itself, it is still registered but marked: claiming it, merging it into another instance or moving it to a tenant clears them first and is refused if that fails again. Instance keys are now checked for duplicates without regard to case, and new WeChat multi-instance keys may only contain letters, digits, underscores and hyphens.
- The settings "Enable Worldbook" and "Enable Chat Memory" (formerly titled "… for This Channel") and related descriptions now say that they can be set globally, per instance and per chat.
- Tenant admins can only create read-only members; another admin has to be created by the platform owner. New console accounts need an initial password of at least 12 characters, whoever creates them. The account that created a member is recorded.
- Conclusions from CC tasks sent directly from the console are now kept for the console only: no group or private chat recalls them any more, with or without per-domain memory. The console still sees the whole workspace when it sends a task, and the memory pages still list these conclusions. CC tasks started from a chat are unchanged.

### Added
- Importing a SillyTavern character card into an instance whose advanced prompt slots are off now asks whether to turn them on, when the card brings post-history instructions (which are otherwise saved but not sent). "Turn on and import" turns the slots on for that instance in the same import, with the same confirmation text, permissions and change log as the settings page; "Import only" keeps the previous behaviour. The dialog also lists chats that keep the slots off on their own. If turning on fails, the character is still imported and the result says so.
- The affection page now shows a person's relationship milestones next to the admin notes, with where each one lives (milestones are long-term memory, notes belong to the worldbook). A milestone can be deleted (it stays recoverable on the memory page) or opened on the memory page, and a milestone on the memory page can jump back to its affection entry. The detail shows what the bot calls the person, and the call name can be edited together with the impression. The memory page can filter memories by source, including relationship milestones, and the prompt-round detail lists the milestones the bot saw in that round.
- New built-in plugin "Affection Tools", on by default. The bot can now change how much it likes someone on the spot when it feels the relationship really changed, and remember what to call a person from now on (a nickname or pet name). It decides by itself whether to use either; nothing else is added to its instructions. Its own adjustments share the daily and weekly limits with the background affection evaluation, are capped per call, only apply to people who have spoken in the current conversation (never to itself), and have a cooldown per person; the evaluation does not count the same conversation again for someone the bot already adjusted. The reason it gives is left out if it would quote what someone said. The name it chose shows up in its notes about that person, and resetting someone's affection or clearing the impression also clears it. When someone shows up again after a week or more (configurable, can be turned off), the bot is told how many days it has been; affection never decays on its own. The plugin can be turned off in plugin management, and its methods only appear where the affection system is on.
- Relationship milestones in the affection system: when the bot's relationship with someone moves to a new stage, it now remembers that as a long-term memory ("on 10 November, X and Y went from acquainted to friendly, because …") and sees the latest one alongside its feelings about that person. Small back-and-forth around a threshold is ignored, at most one milestone per person per day is written, and the reason is left out if it would quote what someone said. Only the bot's own evaluation creates milestones; admin adjustments do not. Requires long-term chat memory for the chat; resetting someone's affection also removes their milestones. On by default, can be turned off per instance or chat.
- New built-in plugin "Message Recall", on by default. In QQ groups (OneBot V11) the bot can now recall a message itself, for example a password or private key someone posted by mistake, or its own wrong message. The model decides whether and when to use it and what to say; nothing else changes in how it replies. It points at a message with the sender id and time already shown in the chat history, so the history sent to the model is unchanged. The bot can only recall messages in the current group that it has on record, at most 10 recalls per group per hour by default (plugin setting; only recalls actually sent to the protocol end count), and recalling someone else's message requires the bot to be a group admin or the owner (an admin cannot recall the owner's or another admin's messages). When a recall fails, the model gets the protocol end's reason and both sides' group roles so it can explain. Each call is logged without the message text. The plugin sleeps until needed, so it adds roughly 100 prompt tokens per round. Recalled messages are handled as before: the bot can still see them.
- Pull requests now also run frontend type checks and lint in CI.
- Ops tools the bot can call itself (first part, read-only, off by default). With `OPS_AGENT_TOOLS_ENABLED` on, an operator on the allowlist (`OPS_AGENT_OPERATORS`; empty means the ops bot's list) can ask in plain language, in their own private chat or in an allowlisted ops group (`OPS_AGENT_GROUPS`) on a platform-owned instance, about instances, tenants, today's usage, a chat's quota or recent errors, and the bot looks it up. A round only gets the tools when every message that triggered it came from an allowlisted operator; each call is checked again right before it runs and logged. The settings are platform-only and hidden from tenants; with the switch off nothing changes.
- Ops tools, second part: the bot can also act on what an operator asks: enable or disable an instance or a chat, restart a built-in NapCat protocol end, suspend or resume a tenant, give a chat extra quota for today, and switch the ops tools off. Every change is reversible; after each one the bot posts a fixed-form receipt in the chat, written by the host and not by the model. Once a round has read outside text such as the error log, writes are refused until the operator asks again, and there are per-round and per-hour limits. `/na_ops` write commands now run directly instead of sending a confirmation link (the link and its console page are gone), and `/na_ops tools on|off` switches the ops tools.
- Ops tools, third part: every ops tool call and every `/na_ops` write is kept in an audit table for a year (who, where, which tool, what happened; arguments redacted, no error text). A write is not carried out if its audit row cannot be written. Receipts carry the record number, `/na_ops audit` lists the latest records, and the console has a new platform-only page, Ops audit. One new table (database migration 36, applied on start-up).
- Ops tools: write operations are also refused when the chat history the bot is reading contains messages from people who are not operators, or pushed outside content (timers, CC results, GitHub events, mail). Keep the ops group to operators only; see `docs/operations.md`. `/na_ops tools off` can no longer turn the tools on when saving the setting fails.
- Per-chat daily quota: counting replies no longer scans the message table for quiet chats, and a full recount also clears token counts that have no ledger entries.
- Per-chat daily quota (off by default). The platform owner can give each group and each private chat a daily allowance in replies or in tokens, and choose whether going over only sends an alert or pauses the chat until midnight. A paused chat answers the first mention of the day with a short notice that the platform owner or the tenant can word (it goes through the output filter), and then stays quiet; reminders and plugin pushes start no reply while it is paused. Tenant admins can lower the allowance for their own chats, not raise it. Alerts go to the platform owner's channels and to the tenant's own instance webhook, at most one message per 10 minutes per destination. A new "Channel Quota" console page lists every chat's usage and remaining allowance for the day, with per-chat history and token use by kind of call; the instance page and the chat detail show the same. Moving an instance between tenants clears the previous tenant's own limits on it. When the allowance is counted in tokens and a chat is paused, its memory consolidation and affection evaluation pause too and catch up the next day. Token counts can be recounted from the usage records, and yesterday is recounted automatically after midnight.
- Long-term memory that does not need a CC workspace (first part, off by default). A new global switch `MEMORY_DOMAIN_SCOPE_ENABLED` turns it on; while it is off, memory behaves exactly as before. With it on, chat memories are kept per memory domain (an instance, or an instance group) and preset instead of per workspace, so any group or private chat can have memory without binding a workspace, and binding or unbinding a workspace no longer makes a chat forget. A chat consolidates and recalls memories only when the memory system and the new per-chat setting `MEMORY_ENABLE_FOR_CHAT` are both on; the platform owner turns it on per instance or chat, and tenant admins can turn it off for their own but not on (they cannot write an override that keeps it on either, and saving or reloading a settings layer cannot turn it on). For now a chat recalls only its own memories (and, for groups bound to the same workspace, each other's); recall across chats comes later behind per-direction settings that are off by default. Memories never cross tenants or instance groups. The switch can be turned off or on while the bot runs (no restart needed, but not while a memory rebuild is running): already queued consolidation does not write into the other kind of storage, and a chat never consolidates twice at the same time. Existing vectors are updated in the background within seconds of turning the switch on (at start-up or while the bot runs, no restart needed), or with the ops command `memory_backfill_payload -y`; until then they are not recalled from the vector side. The recall budget (`MEMORY_CONTEXT_MAX_ITEMS`, `MEMORY_CONTEXT_MAX_LENGTH`) and the consolidation model groups can now be set per instance. Includes a database migration that only adds columns and indexes.
- Long-term memory (with the switch above on) now records which people each memory is about, and can be recalled across chats if you allow it. Three per-direction settings, all off by default and settable per instance or chat (tenant admins can set them on their own instances): group to group, group to private chat, private chat to group, each "off", "related" or "all". "Related" goes by the people the memory is about, not by who is asking: a group memory is recalled in another group only if everyone it is about has spoken in that group recently (30 days by default), and in a private chat only if the other person is one of them. A chat always recalls its own memories; private memories follow the person (including accounts merged into the same person) and never appear in someone else's private chat; nothing crosses tenants or instance groups. Memories recalled from another chat are given as summaries only: the memory tools do not reveal which chat they came from or quote the original messages.
- Long-term memory (with the switch above on) keeps a short rolling summary per chat and preset: what the chat has been about lately, running jokes, who is doing what, agreements. It is produced by the same model call that consolidates memories (no extra call), keeps the last five versions, and is shown only in its own chat, before the recalled memories, as untrusted reference material; after a blocked reply it is left out once, like the recalled memories. It can be turned off per instance or chat (`MEMORY_CHANNEL_SUMMARY_ENABLED`); its length is capped by `MEMORY_CHANNEL_SUMMARY_MAX_CHARS` (400 by default). With the switch on, consolidation also treats the chat transcript and the previous summary as untrusted material and is told not to quote messages verbatim or carry instructions into memory. It also no longer stores the bot's own role-play lines, persona and self-description as facts (only promises the bot made to someone are kept, marked as said by the bot), keeps account numbers out of memories (people are named by nickname; numbers of people in the batch are replaced even if the model writes them), and skips a new memory that is nearly the same as a recent one of the same chat and preset (`MEMORY_CONSOLIDATION_DEDUP_SIMILARITY`, 0.92 by default, 0 turns it off).
- Long-term memory (with the switch above on) does not repeat itself: a memory injected into a chat is not injected again automatically for the next few rounds (`MEMORY_RECALL_COOLDOWN_ROUNDS`, 3 by default, 0 to turn off), unless the current message is clearly about it; the memory tools are not affected. A workspace rebuild now also rebuilds the chat memories of the chats bound to it (old chat memories are removed even for chats with no messages in the look-back window), and the new ops command `memory_rebuild_channel <chat_key>` rebuilds one chat's memories (it only prints an estimate of the work unless you add `-y`).
- Long-term memory management API (`/api/memory`, the backend of the memory page below): list memories by domain, instance, preset, chat, person, status, time and keyword; view, trace back to the original messages, edit (including who a memory is about, limited to people who spoke in that chat), freeze, protect, adjust weight, quarantine and restore, delete, or delete for good (the default is still a soft delete); bulk actions show the count first and only run when the same count is sent back. The platform owner sees everything; a tenant admin sees only their own instances' memories, and anything else answers like a missing ID. Quarantined memories are not injected and not found by the memory tools, but are kept until an admin restores or deletes them. Deleting for good also removes the memory's people, its vector, the relations taken from it and the episodes that contain it; chat history itself is not deleted.
- Long-term memory now records, for each agent reply, which memories, which summary version and whether the affection block went into the prompt and how long each was (references and sizes only, never the prompt text); each chat keeps its last 20 rounds for 30 days by default. If a reply is blocked by content moderation or refused by the provider, the memories it used are counted, and one that shows up in 3 blocked replies is quarantined automatically (adjustable, 0 turns it off). Channel summaries can be edited, rolled back and have their automatic updates paused. With the long-term memory switch on, the memory tools the agent uses are renamed and no longer say "workspace", and a quarantined or deleted memory can no longer be fetched by its ID. Moving instances between tenants can now show what memory each instance carries and optionally delete it together with its own affection data; the join-group preview shows how many memories become visible to the group.
- Memory page in the console (Chat Management → Memory; the platform owner and tenant admins, not read-only members). It follows the instance switcher in the top bar. Four tabs: memory items (paragraphs and episodes, filters kept in the URL, a detail dialog to edit, trace the original messages, freeze, protect, adjust weight, quarantine, restore, delete or delete for good, and bulk actions that always show the count first), quarantine (with the reason and how many blocked replies a memory was in), channel summaries (versions, edit, roll back, pause automatic updates) and prompt details (per chat, what each reply injected and the current state of every memory it used, with quarantine and delete right there). The chat detail page gets a Memory tab with that chat's prompt details and summaries; the chat detail response now includes the chat's `adapter_key` and `instance_key`. Saving a tenant's instances first lists the instances that change owner with how much memory, summary and affection data each carries, with an unchecked box to delete it; joining a domain says how many memories become visible to the group.
- The output filter can now also filter what long-term memory stores: with "filter before memory" on (and the output filter itself on), matched fragments are replaced in the memories being written and matched entities and relations are dropped. Memories stored earlier are not changed. Off by default.
- Output filter. The bot's outbound text can be checked against a word list and regular expressions before it is sent; a matched fragment is replaced with `**Filter**` (or the whole message, if you choose), and the replacement text can be changed. Meant for account owners who do not want the bot to say certain things and risk a ban. Off by default with empty lists; find it under the new "Output Filter" settings category. Like other overridable settings it has a global default and per-instance overrides, and tenant admins can set it for their own instances. Matching ignores full-width/half-width and case differences and spaces or zero-width characters inserted between letters, so splitting a word does not get it through. Overly complex regular expressions are refused to keep sending fast, and the settings page lists refused rules and how many times each rule matched per instance (the message text is not stored). An optional starter word list can be viewed and copied from the same panel; it is not enabled unless you paste it in. It covers replies, command output and plugin messages sent through the framework, and on OneBot V11 also plugins calling the send APIs directly (including forwarded-message nodes and AI voice text). It cannot see messages that a plugin sends by talking to the protocol end or a platform SDK on its own. With the filter off, messages are unchanged.
- OneBot V11 can check whether the bot is still in each QQ group. Every 6 hours by default (new OneBot setting "Bot Group Membership Check Interval (hours)", 0 turns it off), or right away from the chat list, an instance's group list is compared with its group chats, and the chats of groups the bot is no longer in are marked "Bot not in group". This only marks: no chat is disabled and no message is sent. When the group list looks unreliable (the request fails, the list is empty, it shrank by more than half since the last check, or a group someone spoke in during the last hour is missing from it), nothing is marked that round. The chat list can be filtered by the mark, and marked chats can be disabled in bulk after a preview; that is a manual disable, so they are not re-enabled automatically. A mark clears itself when the group speaks again or the bot rejoins. Platform owners and tenant admins can check their own instances. Private chats are not checked.
- The output filter's optional starter word list now has content: about 60 Chinese and a few English entries for explicit sexual content, porn and solicitation lures, and abuse (no political terms; a few medical terms are included but commented out). It is still only offered for copying on the settings page and is never applied by itself.
- Worldbook management API (`/api/worldbook`). Books can be bound to a memory domain, a preset, a chat or a person; entries can be created, edited, quarantined and restored, imported from and exported to SillyTavern World Info JSON (fields this edition does not use are kept and written back on export), and tried against a chat with a trigger test that calls no model and changes nothing. The platform owner sees everything; a tenant admin sees only their own instances' books, and anything else answers like a missing ID. Entries written or edited by tenant admins are always treated as untrusted. Regular-expression keys are checked when saved and limited in time when run. Includes a database migration that creates two tables and adds two columns with defaults to an existing one.
- Worldbook injection (off by default; with it off prompts are unchanged). New settings category "Worldbook": an on/off switch that the platform owner and tenant admins can set per instance and chat, a character budget per round that tenants can only lower, a global entry limit per round and a global threshold for automatic quarantine. With the switch on, each reply evaluates the books that apply to the chat over the same recent messages the history uses and injects matching entries after the persona, before the recent messages, or at a depth inside the history, within the budget. Entries written by tenant admins are injected as untrusted reference material and left out of the round after one the model provider blocked; entries that keep appearing in blocked rounds are quarantined automatically. Each reply's details on the memory page list the worldbook entries it used, the ones the budget left out and why, and their current status; tenants do not see books, titles or content from books outside their instances. Changing a chat's key, moving or purging an instance, and transferring instances with "clear memory" ticked now carry or delete the worldbooks too, and the transfer and join previews count them. A new endpoint saves a one-line note about a person as a constant entry in that person's book for an instance, creating the book if needed. The trigger test now uses the chat's real settings and shows the rendered text for each position.
- Worldbook page in the console (Chat Management → Worldbook; the platform owner and tenant admins, not read-only members). It follows the instance switcher in the top bar. Three tabs: books (filters kept in the URL, create a book, import a SillyTavern World Info file as a new book), quarantine (restore or delete) and a trigger test (pick a chat, paste some text or use its latest messages, and see which books apply, which entries match and why, what the budget kept, and the text each position would get; it warns when the switch is off for that chat). A book's page has its settings, the entry table with enable/disable, quarantine/restore and delete, appending another file with an import report (including keys whose regular expression was rejected), and export. The entry dialog edits keys, logic, regex, constant, content, order, position and depth, plus scan depth, case and whole-word overrides and sticky/cooldown/delay, which can also be set back to "use the book's setting". Only the platform owner can mark an entry as host content. The preset list offers the presets a book can actually be created for. Each reply's details on the memory page gain a worldbook section with quarantine and disable right there; the affection detail lists the notes kept about a person and adds a "write a note" button; the instance transfer dialog shows how many books and entries each instance carries. In a single-instance deployment, new books and notes go to that instance. During a reply that takes several steps, worldbook entries are included once, not again with every step.
- SillyTavern character card import and export, first part: the backend API (`/api/tavern`; the platform owner and tenant admins, not read-only members). A card (PNG or JSON, V1 / V2 / V3) can be inspected without saving anything, then imported as a new preset: its description, personality, scenario, example dialogue and system prompt are assembled into the preset text with a template the platform owner can change (`TAVERN_CARD_TEMPLATE`); greetings, post-history instructions, the depth prompt and the card's regex scripts are kept with the preset; the embedded lorebook becomes a worldbook bound to that preset. Everything in a card is treated as untrusted input: file, chunk, JSON and field sizes are limited, only the card chunks of a PNG are read (`tEXt`, and compressed `zTXt` with the decompressed size capped), the image is re-encoded, nothing is switched on by importing, lorebook entries are always reference material whoever imports them, and regex scripts that fail the safety check (or would render HTML) are imported disabled. Presets can be exported back as PNG or JSON cards; an unchanged import exports field for field the same. Sharing a preset to NekroCloud now carries its card data, and downloading such a preset restores it.
- SillyTavern character cards at run time. Presets imported from cards now behave like their cards: macros such as `{{char}}` and `{{user}}` (the cleaned nickname of the member who triggered the reply) are expanded, the depth prompt is placed in the history at its depth, and the greeting is sent once when a chat switches to the preset or after `/reset`, before the usual reply. Card cleanup rules tidy the bot's replies before the output filter runs. A rollback switch "Tavern compatibility" (on by default) turns all of this off; presets without card data are not affected. Advanced prompt slots — post-history instructions, an auxiliary prompt and an answer prefill, set globally, per instance or chat and per preset — are off by default and only sent where an administrator turns them on (turning them on asks for confirmation; every change is logged without the text). The prefill is only sent to model groups whose new "prefill mode" setting allows it. Administrators can preview the full prompt a chat would send, and trial it once with their own model group: the trial is never sent to any chat or stored, and tenants can only use their own model groups. The admin pages for all of this are described in the next entry.
- SillyTavern character cards in the console. The preset page has an "Import tavern card" button: pick a PNG or JSON card, read the report (card details, the assembled preset text, the system prompt, post-history instructions and depth prompt each shown in full with a checkbox, greetings, the lorebook, and each cleanup rule with an on/off switch and the reason it starts off), then import; a result page lists anything that could not be applied. Card text, including the creator's notes, is always shown as plain text. Every preset can be exported as a PNG or JSON card, presets imported from cards carry a "Tavern card" badge, and sharing or syncing such a preset to NekroCloud now says plainly that the whole card goes with it. Editing a preset has a second tab, "Tavern extension", for the nickname, macros, the card's source fields (with "reassemble"), greetings, post-history instructions and prefill (showing whether this instance actually sends them), the depth prompt and the cleanup rules (a rule that kept timing out is marked; a rule that was switched off on import can stay in the table without blocking saves); global presets can be viewed read-only from an instance. Turning on "Advanced prompt slots" in the settings now asks for confirmation, model groups have a "Prefill mode" choice, and prompt round details show the card and slot state of each round. A new page, Chat Management → Prompt Lab (platform owner and tenant admins), previews the full prompt a chat would send (it still works when the bot is offline, with a placeholder for the bot's own account), runs a one-off trial with your own model group, and lists changes to the advanced prompt settings.

Right after a chat switches presets, the bot's replies (including the new preset's greeting) are cleaned with the new preset's rules straight away instead of the old one's for up to ten seconds. Previewing another preset in the Prompt Lab now also uses that preset's worldbook (the chat summary and affection block still follow the chat's current preset, and the page says so). The Prompt Lab's selects show their default choice when collapsed, and full-screen dialogs on phones are no longer see-through in dark mode. Note for operators: whatever the platform writes into prompt settings that apply to tenant chats is sent with every round to the model group those chats use, including a tenant's own; the preview hides it from tenants on the page, but it is not a way to keep it secret.

PNG cards whose data is stored compressed (`zTXt`) now import; a compressed card that would unpack beyond the card size limit, or is damaged, is rejected as a whole. Cards can be up to 20 MiB, but the platform's upload limit (`MAX_UPLOAD_SIZE_MB`, 10 MB by default) still applies, so a default deployment accepts 10 MiB; when a card is too big the message says which limit applied and suggests exporting it from SillyTavern as JSON. Regex scripts marked both "markdown only" and "prompt only" apply to both in SillyTavern, so they are now imported as normal rules instead of being switched off.
- Uploaded image retention (off by default, as upstream). Chat images pile up in `uploads/` in the data directory and were never deleted; busy deployments can gain several GB a day. A new system setting "Uploaded Image Retention (Days)" under Basic Settings (`UPLOADS_IMAGE_RETENTION_DAYS`, 0 = off) makes the bot delete, once a day, images in `uploads/` last modified more than that many days ago (jpg, jpeg, jfif, png, gif, webp, bmp, heic, heif, avif, tif, tiff, any case). Other file types and email attachments are never touched, symbolic links are not followed, and nothing outside `uploads/` is deleted. Only the platform owner can set it: tenants do not see it and instance or chat overrides do not have it. It takes effect without a restart (within 10 minutes), runs 5 minutes after every start-up and then daily, and does nothing at all while it is 0; each run logs one line with how many files and bytes were removed. ## v0.4.5 (2026-11-21)

Two cross-tenant fixes (Web Chat MCP workspace tokens, delivery of CC results), four hardening fixes for long-term memory, more places where text from outside the host reached the model as trusted text, redaction of CC failure messages, and fixes around file paths, attachment names and protocol-end addresses. No database migration, no new dependency, no configuration change; see the upgrade notes.

Published on 2026-11-21 together with v0.4.6 and v0.4.7: the public edition had not been updated since v0.4.4. Coming from v0.4.4, go straight to v0.4.7 and read the upgrade notes of all three versions.

### Fixed
- The Web Chat MCP server can again give a CC workspace its own access token, as upstream does, but only to workspaces that have only ever been used by the platform owner. A workspace's owner follows the chats bound to it, so a workspace that was bound to a tenant's chat and later unbound counted as the platform owner's again, and a token written into it while the tenant could read its files would have worked as the platform owner's account. Every workspace that has ever been owned by a tenant, or shared, is now remembered permanently (in `system/web_chat_mcp_tainted_workspaces.json` in the data directory) and never gets or accepts a token again; create a new workspace if you need the Web Chat MCP there. Workspace tokens were not issued at all since v0.4.3. The first start-up with this version cannot know about earlier history: if a workspace was bound to a tenant's chat before and is the platform owner's again, do not enable the Web Chat MCP entry on it.
- Results that a CC workspace reported for later delivery named their target chat themselves, so a manipulated workspace could push a result into, and trigger the agent in, any chat, including one belonging to another tenant. Results are now delivered only to chats currently bound to that workspace; anything else stays in the workspace's own communication log. The console's force-cancel button trusted the same report to decide which chat's task to cancel and now does so only for chats bound to the workspace. A malformed result can no longer stop result delivery for every workspace.
- CC error messages, from delegated tasks and from commands sent directly in the console, are now redacted before they reach the model, the workspace communication log and the runtime status shown in the console: the platform's configured secrets and the CC model presets' tokens are replaced, and common credential shapes (`Bearer …`, `sk-…`, `api_key=…`) are masked. Successful results are unchanged.
- The summary of a shared card (title, description, sharer nickname, link, all chosen by the sender) was shown to the model inside a tag reserved for host-written content. It is now wrapped as untrusted content like forwarded messages.
- Minecraft join / quit / death / achievement notices passed player nicknames and server texts to the model as a system message. They are now delivered as untrusted content with a fixed host summary, and still trigger the agent.
- The file-saving helpers available to plugins and adapters (`FileUtils.get_upload_file_path`, and `bytes_to_file` / `base64_to_file` in the SSE adapter) used the given file name as is. A name such as `../../x`, an absolute path, or one containing control characters could write outside the upload directory or fail on disk. They now keep only the last path segment, drop control and reserved characters, and refuse to write when the resolved target leaves the directory, like the download helpers already did since v0.4.3. Nothing in this edition passed such names to them; this closes the door for plugins that do.
- The Web Chat MCP tool `send_web_chat_file` answered differently for a path outside the allowed directories depending on whether a file existed there, which let the caller (the platform owner only) check for files on the host. The allowlist is now checked first, and any path outside it gets the same "not allowed" answer whether or not it exists.
- The first memory consolidation of a chat started from the chat's oldest message, so a chat with a long history spent a long time consolidating old messages while current conversation never reached memory. The first run now only sets the starting point to the chat's latest message and processes nothing; consolidation continues from there. Chats that already have a consolidation cursor are unchanged, and rebuilds still cover history. The messages that triggered that first run are not consolidated.
- Recalled memories were reinforced as soon as they were retrieved, before the reply was generated: a reply that needed several iterations reinforced them several times, and a reply blocked by the provider's content policy still reinforced the memories it had injected. Reinforcement now happens once per reply, after the reply finished normally; blocked, refused, failed or unfinished replies reinforce nothing. After a reply ends with a content block or a provider refusal, the next reply in that chat injects no recalled memories at all (the same in-memory chat mark that already suppresses affection descriptions), until a reply succeeds.
- Memories recalled automatically into the prompt were inserted as plain text. They are distilled from chat, so their wording is controlled by chat members. The recalled block is now introduced as reference material, wrapped as untrusted content with the round's one-time token like the other blocks of this kind, and every line is cleaned to a single line of limited length. The "current focus" lines, which repeated recent messages, are gone; the recent messages follow the block anyway.
- When memory consolidation failed (for example an invalid API key, a rate limit, a timeout or a provider error), the batch of messages was treated as processed and never reached memory. Such failures no longer advance the cursor: the batch is retried on the next run, and from the third consecutive failure the chat backs off (30 minutes, doubling, at most 6 hours) without calling the model. Only batches that cannot succeed on retry (blocked by the provider's content policy, a provider refusal page returned as the reply, or a reply still unparsable after retries) are skipped, and the chat keeps a count of skipped batches. A memory rebuild that hits a temporary failure now marks that chat as failed instead of silently dropping the batch.
- The e-mail adapter's new-mail notice passed the sender name, subject and attachment names to the model as a system message, so anyone able to write to the mailbox could phrase instructions there. The notice is now delivered as untrusted content: those fields are wrapped and cleaned, and only host-written text (the account, the mail id and how to fetch the mail) stays trusted. The notice still triggers the agent.
- Plugin tasks can hand external text to the agent as untrusted content: `notify_agent` now accepts an untrusted result besides a plain string. Plain strings behave as before.
- The outbound addresses of a protocol-end connection (the reverse WebSocket and HTTP-report targets a platform owner can configure) were checked with a different URL parser than the one the protocol end uses to connect, so a crafted address (for example with a backslash, percent-encoded or shorthand numeric host) could pass the public-network check while the protocol end connected to an internal host. The address is now accepted only in a strict shape that every parser reads the same way, and only its host and port are checked. Addresses with user info, non-ASCII hosts or numeric shorthand hosts are refused on save (write internationalised domains in their `xn--` form).
- The file name stored with an inbound file or image could differ from the name the file was saved under, so the path shown to the model could point at a file that did not exist (for example `a?b.txt` is saved as `ab.txt`). The stored name is now the name the file was saved under. File names also lose trailing dots and spaces, and Windows reserved device names (`NUL`, `CON`, `COM1`, ...) fall back to a generated name instead of being written to a device.

### Security
- **Please update if you host tenants: a tenant could take over an account you were about to bind to your own OneBot instance.** While an account is not bound to an instance, a connection may also present the token of any instance still waiting for an account (or nothing at all when `ONEBOT_ACCESS_TOKEN` is empty). A tenant with the token of its own waiting instance could connect first with your bot's account; after you bound, adopted or claimed the account, that connection stayed, its messages were handled as your instance's messages, your real protocol endpoint was refused as a duplicate, and what NekroAgent sent to the account went to the tenant. A connection now counts for an account only if the token it presented is the one the account's instance currently requires: when an account binding changes, connections that no longer match are closed, and messages arriving on such a connection are dropped.
- An HTTP-reported event for an account that was not bound yet could keep that account's WebSocket endpoint refused as a duplicate until restart. A WebSocket that passes the token check now takes the account over from such a leftover.
- **Incoming attachment names could write files outside the upload directory (affects v0.4.2 and earlier).** With the QQ official bot adapter (`qqbot_openclaw`), the name of an incoming attachment was used as it was when the file was saved, so a name containing `../` or an absolute path could put the file outside the upload directory, for example into the plugin directory. - **A tenant could run commands in another workspace's sandbox through the MCP test button.** Testing a stdio MCP server in a workspace whose container had never been started fell back to any running workspace. A test for a given workspace now only runs in that workspace's own container.
- **The MCP test that tenants can use connected from the server to any address.** For tenant accounts, http and sse MCP servers are now tested only on public addresses (no loopback, private, link-local or cloud metadata addresses), redirects are not followed, and every request and the actual peer of every response are checked again. A refused address is reported as "address not allowed" without connecting. Tests run by the platform operator are not restricted.
- **Text from the CC workspace and from GitHub webhooks could act as system instructions.** CC's results and error messages, the stored description of a delegated task, and the titles, bodies and comments of issues and pull requests in a subscribed GitHub repository were pushed into the conversation as system messages, which the model is told to trust, and triggered the agent at once. Anyone who can open an issue on a subscribed repository, or influence what CC reads (workspace files, web pages), could inject instructions this way. This text is now stored and shown to the model as untrusted content, wrapped like other tool results; only the plugin's own notice stays outside (with the workspace name, repository and event name quoted on one line). The agent is still triggered as before. Issue and pull request titles are folded into one line.

- **The quota whitelist trusted any sender ID.** The same number on another platform, an SSE caller's `from_id`, an email sender or a number reported by a tenant's own protocol endpoint skipped the reply quota. The whitelist now works like `SUPER_USERS`: bare numbers are QQ numbers, other platforms use `adapter:ID`, and only sources you control count.

## v0.4.2 (2026-11-03)

**Security release: please update.** This is the first public release since v0.3.0. Versions 0.3.1, 0.4.0 and 0.4.1 were not published on their own; everything they contain is included here. Updating from v0.3.0 fixes, among other things (details under Security):

- Stored cross-site scripting: an email to the bot's mailbox, or HTML in a chat message, plugin document or announcement shown in the console, could run script as the logged-in admin.
- Code running in the sandbox could run arbitrary code inside the NekroAgent process.
- Chat-command super users could be impersonated, so a tenant, an anonymous protocol endpoint or a caller of the SSE adapter could run shell commands through the bot.
- With an empty `ONEBOT_ACCESS_TOKEN`, any OneBot endpoint that connected could use the bot and your model quota.
- Image and file downloads, and model endpoints entered by tenants, could reach the server's internal network through certain international host names.
- Several ways for one tenant to read or change another tenant's channels, instances, timers or chat history.

This edition is still based on NekroAgent 2.3.3 and is now plugin-compatible with 2.4.0. It includes most of upstream 2.4.0's features and fixes (knowledge-base batch operations and zip import, plugin call priority, command permissions and channel scope, WeChat iLink fixes and others); upstream 2.4.0's web chat adapter and MCP online test are not included yet.

Some of these fixes change behaviour. Read the upgrade notes before updating, especially if `ONEBOT_ACCESS_TOKEN` is empty, if you use `SUPER_USERS`, or if you host tenants.

### Security
- **Please update: an email or a chat message could run script in the console as the logged-in admin.** The email viewer injected the HTML body into the page, and the Markdown renderer used for chat history, email `.md` attachments, plugin docs, skills and announcements rendered raw HTML without filtering. Email bodies are now shown in a fully sandboxed frame with a strict content security policy (no scripts, forms, popups or self-navigation), and Markdown no longer renders raw HTML except in the bundled adapter docs.
- A late "unauthorised" answer to a request made with an old login no longer logs out a session that was just created.
- Plugin web pages only serve web assets (HTML, scripts, styles, images, fonts, JSON, WebAssembly, media); plugin source files, databases and configuration files are never served.
- **Please update: code running in the sandbox could run arbitrary code inside the NekroAgent process.** The sandbox's plugin-call endpoint decoded request bodies with `pickle`, and sandbox code can read the callback token it needs. Requests from the sandbox are now plain JSON with explicit type tags, decoded only after the token has been checked; NekroAgent rebuilds tagged values with fixed constructors and never looks up a class or function named in a request. Answers to the sandbox are checked against a whitelist before they are sent, and the sandbox decodes them with the same whitelist.
- Requests from the sandbox are limited: 1 MiB per call, plus limits on nesting, number of values and containers, string and integer length, on how many calls one sandbox can have in transit or running at once, and on how much decoding time it can use per second. Requests are decoded one at a time. This limits how much a busy or hostile sandbox can slow other conversations down. Calls refused because the server is busy are retried automatically; oversized or malformed requests come back to the sandbox as an error instead of tying up the server.
- Methods whose result the AI reads as a system message no longer repeat their arguments verbatim: echoed arguments are shortened to one line, quoted, and stripped of invisible characters. Invisible characters that can hide text are also removed from untrusted content, while emoji sequences, flags and scripts that need joining characters (such as Persian and Devanagari) are kept intact.
- **A sandbox method can no longer reach another channel's or another tenant's data by passing its `chat_key`.** `find_history_travel` / `find_history_travel_range` (chat history), notes and character status now accept only the current session and answer exactly as if the channel did not exist. The range search also no longer follows a message ID that belongs to another channel.
- Timers (including recurring timers, whose 4-character `job_id` could be guessed), sending messages, AI voice, group titles, Minecraft rich text and RCON, the Bilibili live methods, forwarding an email attachment and `draw(send_to_chat=...)` work for channels of the same tenant and are refused across tenants. In a deployment where no instance belongs to a tenant (the default), every channel stays reachable as before, including Telegram chats.
- **Content from outside no longer comes back to the model as a system message.** Search results, emails, chat history, knowledge-base and memory results, RCON output, skill documents and the skill list, CC collaboration context, `view_str_content` and `view_image` descriptions are returned as `UntrustedToolResult`: stored as a tool-result row, wrapped in an untrusted block with the token of the turn that reads it, and never passed back through the sandbox. Plugins that return a plain string keep the old behaviour.
- Long history lines are cut inside the untrusted block instead of across it, so the block's tags are never lost. `view_str_content` returns at most 16000 characters per call.
- Video files on the local disk are only read for the built-in NapCat that NekroAgent itself started, only inside that instance's data directory and only if they are video files; a remote protocol endpoint cannot make NekroAgent read local files. A file fetched through `get_file` is used only if its name and size match the chat record, because NapCat's `get_file` looks files up by name.
- A video playback address stops working at once when its user is banned, loses Admin rights, leaves the tenant or changes their password.
- Video streaming has limits: 6 streams per user and 32 in total, with at most 8 per tenant; every tenant keeps 2 for itself and the last 8 are never handed out beyond those guaranteed shares, so busy tenants cannot lock out the others or the platform. There is also a 60-second timeout for a browser that stops reading and a 64 MB seek limit on sources that do not support Range. A stream cut by these limits, or by the 512 MB size cap, ends as an interruption, never as a complete (truncated) video.
- An anonymous request whose path contains `<`…`>` can no longer turn into a server error when debug logging is on.
- A forged video playback address is refused without a database lookup; a malformed one can no longer cause a server error.
- On a Windows host, a path reported by NapCat that names another drive or a network share is refused before any file lookup, so no connection to that share is made. The real path of an opened file is taken from the file handle, not from a `/proc` path that on Windows would point into the root of the drive.
- **A tenant could reach another tenant's instance through a same-named instance of another adapter.** Instance keys are only unique within one adapter, but tenant checks compared the key alone. Checks and filters now use the adapter and the key together, new instances can no longer take a key another adapter already uses, and NekroAgent logs a warning at startup for each key that existing data already shares.
- WeChat iLink multi-instance management had no tenant check, and a few adapter maintenance endpoints that act on the whole deployment (`qqbot_openclaw`, the `wechat_openilink` login status) were open to tenant admins. They are now limited to the platform owner; tenants only see and manage their own WeChat instances.
- Per-instance plugin credentials are redacted before a sandbox method's result or error goes back to the sandbox, like global ones.
- Knowledge-base zip import treats the archive as untrusted: absolute paths, drive letters, `..` and control characters reject the whole archive; file and total sizes are limited by the bytes actually written, not only by what the archive declares; only stored and Deflate entries are accepted; symlinks and macOS metadata are skipped; extraction runs off the event loop, at most two imports at a time.
- **Moving an instance to another tenant, or disabling it, could be undone by the next WeChat iLink session renewal or instance health check**, which saved the whole instance as it had read it earlier. Status updates and renewals now only write their own fields, so tenant assignment, the enabled switch, the bound account and the name stay as the platform admin left them.
- **A disabled, archived or deleted instance could be switched back to a running state by its own connection, a session renewal or the health check**, and a deleted instance revived this way could hold the same account as another instance. Automatic status updates now only apply while the instance is enabled and not disabled, archived or deleted; only the platform admin can bring an instance back.
- **Please update: chat-command super users could be impersonated.** Anyone whose user ID was listed in `SUPER_USERS` counted as a super user on every adapter and through every source, so a tenant's own OneBot protocol endpoint, an anonymous endpoint that connected while the deployment token was empty, or a caller of the SSE adapter could present a listed number and run shell commands; tenants could also read the list. A super user now needs a list entry for the right platform and a trusted source. Plain numbers are QQ numbers on OneBot; other platforms use `adapter:ID`. Adapters whose sender ID is filled in by the caller or a relay (SSE, email, Bilibili live, Minecraft, wechatpad) never count. OneBot counts only on a claimed platform instance whose token has never been visible to a tenant, and only for messages on a connection that presented that instance's current token. NekroAgent keeps fingerprints of tokens that tenants have had; if that record is lost or damaged it is rebuilt before the next check, and until then no OneBot super user is accepted. Moving an instance between the platform and a tenant is refused while that record cannot be written. `SUPER_USERS` is hidden from tenants, also in the channel's effective settings, and only the super admin can change it or reset the system settings.
- **Image and file downloads, and the model endpoints tenants enter, could reach the server's internal network through a host name with certain international characters** (such as `ß`), because the check and the connection spelled that name differently. The check now looks up exactly the host that is connected to.

- **Please update: with an empty `ONEBOT_ACCESS_TOKEN`, anyone could use the bot.** An unknown OneBot endpoint that connected was registered as an unclaimed instance and its messages, notices and commands were processed, using your model quota. Messages of an unclaimed instance are now processed only if its connection presented your current deployment token (and no tenant has had that token). In the shared library these are limited to the platform owner like their single-item versions; in a workspace they follow the workspace's tenant scope. New settings `KB_INDEX_CONCURRENCY`, `KB_BATCH_MAX_SIZE`, `KB_BATCH_CONCURRENCY`, `KB_ZIP_MAX_UPLOAD_SIZE_MB`, `KB_ZIP_MAX_EXTRACT_SIZE_MB`, `KB_ZIP_MAX_FILES`.
- **Built-in qbob for QQ official bots.** [qbob](https://github.com/Loping151/qbob) (AGPL-3.0) can run next to NekroAgent as a separate container (`install.sh --with-qbob`), built on your host from a pinned upstream commit. Connect a bot from the console by scanning the QQ open-platform code or entering its AppID and AppSecret; tenants can watch, switch and reload their own bots. NekroAgent does not include qbob's code. See `docs/qbob-integration.md`.
- **Messages from other programs on the same account.** When another framework shares the protocol endpoint with NekroAgent, its messages are now recorded and visible to the AI, marked as coming from the same account. They never trigger a reply, a command, a quota or affection change, so two frameworks cannot trigger each other in a loop. NekroAgent's own messages are filtered out by message id. Setting: `ONEBOT_RECORD_SELF_SENT` (on by default, can be overridden per channel).
- **Video player in the WebUI.** Chat videos play inline with seeking, through a short-lived signed address tied to the message, channel and user. It works without the video plugin; links are fetched on demand and never stored.
- **Model group names can use Chinese, Japanese and Korean**, plus spaces and common punctuation between characters. Look-alike letters (Cyrillic, Greek, full-width Latin) and invisible characters are still refused. Existing groups stay editable even if their names predate the rule.
- **Batch delete for model groups**, and a warning before deleting a group that configs still use (it only warns, it does not block).
- **Channel admins for chat commands** (from upstream 2.4.0): a channel admin can use `reset`, `stop`, `na_on`, `na_off` and `na_observe` in its own channel only; other channels and "all channels" still need a super user. The platform owner can make someone a channel admin everywhere (`grant_advanced` / `revoke_advanced`); a tenant admin can do it for one of its own channels in the channel's new "Command permissions" tab. Group owners and admins become channel admins automatically only where `COMMAND_GROUP_ADMIN_AS_CHANNEL_ADMIN` is turned on (off by default, can be set per instance or channel; upstream always does this). Super users are still exactly the ones in `SUPER_USERS`. User management and the channel user list show each user's command permission.
- **The console shows which OneBot protocol endpoint an instance uses and whether it reports the account's own messages.** The instance's protocol tab names the implementation and version (SnowLuma, NapCat or another). NekroAgent cannot ask the endpoint whether self-message reporting is on, so it checks whether its own messages come back: when several in a row do not, the page says the setting is probably off, explains where to turn it on in SnowLuma or NapCat, and the log says so once. It notices when the setting is switched off without a reconnect, too. Tenants see this for their own instances.
- **Cold shoulder plugin (off by default).** The AI can decide to ignore one person in the current chat for a while, for example someone who keeps poking it after it said it would stop answering: that person's messages and pokes are still recorded but no longer wake the AI up. Everyone else in the chat, other chats and other bot accounts are unaffected, and chat commands keep working. The AI picks the duration, up to `MAX_MINUTES` (120 minutes by default, can be set per instance); it can only pick someone who spoke in the chat in the last few minutes, and super users are never ignored. The list shows up under the channel's "Plugin data", where it can be edited or cleared, and is emptied when the channel is reset. Turn the plugin on in plugin management.

### Changed
- `exec`, `sh`, `docker_restart`, `docker_logs` and the `conf_*` commands now need a super user; `reset`, `stop`, `na_on`, `na_off` and `na_observe` need a channel admin and only act on the current channel unless a super user runs them.
- The `version` in `pyproject.toml` is now the plugin-compatibility version `2.4.0`; this edition is still based on upstream `2.3.3`. The sidebar shows this edition's own version; `/na_info` and `/na_help` show both.
- CC workspace: letting the AI create a workspace and letting it start a stopped sandbox are two separate settings. Existing configurations keep what they allowed before.
- **Plugin authors, arguments:** sandbox methods can receive `None`, `bool`, `int`, `float`, `str`, `list`, `tuple`, `dict`, `set`, `frozenset`, `bytes`, `datetime` / `date` / `time` / `timedelta` and `UUID`, up to 1 MiB of encoded arguments per call. `pathlib.Path` arrives as `str`, `OrderedDict` as `dict`, `bytearray` as `bytes`, enum values as their plain value. `Decimal`, `complex`, custom classes, `numpy` integer scalars and `pandas` objects fail in the sandbox with an error that names the type and the argument; convert them first (`str()` / `float()` / `.item()`). Calls over a limit (1 MiB, 32 levels of nesting, 100000 values, 10000 lists / dicts, 1,000,000-character strings, 768 KiB of bytes, 100-digit integers) also fail in the sandbox before anything is sent; the message says which argument and how to shrink it. Both cases raise `RpcArgumentError` (a `TypeError` and a `ValueError`), and a call NekroAgent refuses before running it raises `RpcRejectedError` (a `RuntimeError`); code in the sandbox can catch either instead of the run ending. A call refused only because the server is busy is retried automatically for up to 30 seconds before `RpcRejectedError` is raised. Calls from several threads run concurrently, up to 8 at a time.
- **Plugin authors, return values:** the same plain types plus `bytearray`, `complex`, `Decimal`, `OrderedDict` and POSIX paths. Returning a custom class, a `numpy` scalar or a `pandas` object fails with an error that names the type.
- Messages that consist only of a face, sticker, dice or poke can now trigger a reply (private chats, channels set to reply to everything, keyword triggers matching the placeholder).
- The sidebar and login page show the copyright year and "Built on the NekroAgent project" on one line.

### Upgrade notes
- **Back up the database and the data directory before updating.** One database migration runs on the first start (see below).
- **If `ONEBOT_ACCESS_TOKEN` is empty, claim your OneBot instances before updating.** Unclaimed instances no longer have their messages processed unless their connection presented your current, non-empty deployment token. Instances shown as "unclaimed" in the console only keep receiving messages if they already have chat history: those are claimed automatically on the first start (the log lists them; archive any that are not yours). Unclaimed instances without chat history receive nothing until you claim them; the log warns and the console marks them. Instances you created or claimed are not affected. Setting `ONEBOT_ACCESS_TOKEN` is recommended.
- **Super-user chat commands now depend on the connection's token.** Plain QQ numbers in `SUPER_USERS` keep working on your own OneBot instances that have their own token, or that use a non-empty `ONEBOT_ACCESS_TOKEN` no tenant has had. Super-user commands no longer work in tenants' bots, in unclaimed instances, with an empty `ONEBOT_ACCESS_TOKEN`, or through SSE, email, Bilibili live, Minecraft and wechatpad; use the console command page there. Write users of other platforms as `adapter:ID`, for example `telegram:123456`. The startup log warns about each of these cases.
- Protocol endpoints reconnect after the restart, which is all they need. After claiming an instance or moving an account in the console, the protocol endpoint must reconnect once more before super-user commands work there.
- If you host tenants and recalled an instance from a tenant before this update, or a tenant instance used the deployment token, change that token (`ONEBOT_ACCESS_TOKEN` takes effect after a restart; instance tokens cannot be changed in the console yet). The startup log lists the instances concerned.
- NekroAgent keeps its record of tokens that tenants have had under `data/system/`. Keep that directory writable: moving an instance between the platform and a tenant is refused while the record cannot be written.
- Plugins that check `SUPER_USERS` themselves still see the plain list and do not know which platform or connection a message came from.
- **Database migration 27** (`27_20261102191729_unique_adapter_instance_session`) is the only one since v0.3.0, which ended at migration 26. It runs automatically on start. It first merges duplicate WeChat iLink sessions (per instance it keeps the one with credentials, then the most recently updated), records the merge in that instance's events, then allows only one session per instance. A downgrade restores the old index but not the merged-away sessions. To check for duplicates beforehand: `SELECT instance_id, count(*) FROM adapter_instance_session GROUP BY 1 HAVING count(*) > 1`.
- **Plugins: compatibility with upstream 2.4.0.** The `version` in `pyproject.toml` is now the plugin-compatibility version `2.4.0` (this edition is still based on upstream `2.3.3`). Market plugins that require NekroAgent 2.4.0 become installable; plugins that declare a maximum version below 2.4.0 can no longer be installed, as on upstream 2.4.0. There is no new dependency.
- Sandbox method arguments are no longer sent with `pickle`. Sandbox code or plugins that pass `Decimal`, `complex`, custom classes, `numpy` integer scalars or `pandas` objects to a sandbox method now get `RpcArgumentError` and have to convert them first (see Changed).
- Command permission overrides you set to "advanced" before this update are changed to "super user" on the first start, because until now only super users could use "advanced"; the log lists every changed entry. Set them again if channel admins should use those commands. Plugin commands that declare "advanced" become usable by channel admins. `ENABLE_ADVANCED_COMMAND` stays off by default (upstream 2.4.0 turns it on).
- Timers created before this update are kept and keep firing. If you host several tenants, open the timer page as the platform admin after updating and remove timers that one tenant's bot set on another tenant's channel; their description usually gives them away. Single-tenant deployments have nothing to check.
- Built-in NapCat: restart each NapCat container once from the console, so that `reportSelfMessage` takes effect and, on a non-default `NEKRO_EXPOSE_PORT`, the connection uses the right port.
- Remote protocol endpoints: turn on `reportSelfMessage` for the connection to NekroAgent yourself, otherwise other programs' messages stay invisible. Nothing breaks if you do not. On SnowLuma, open the account's OneBot settings in its WebUI, turn on "report self messages" on the reverse WebSocket node that points to NekroAgent and save; it applies at once, without a restart or reconnect. The instance's protocol tab in the console shows whether it works. Messages from other programs on the same account are recorded by default; turn off `ONEBOT_RECORD_SELF_SENT` if you do not want them in the chat history.
- If `SANDBOX_CHAT_API_URL` is exactly `http://host.docker.internal:<port>/api` and the port is not the one NekroAgent is published on (in Docker, `NEKRO_EXPOSE_PORT`), it is corrected on start and the log names the old and new value. If that port deliberately points at another service on the host, such as a reverse proxy, write the host gateway IP or another host name instead.
- If startup logs a warning that an instance key is used by more than one adapter, those instances share presets, plugin settings and memory. Rename or remove one of them.
- qbob is opt-in. When you upgrade by hand, use `docker compose pull --ignore-buildable` (the qbob image is built locally), then `docker compose up -d`. Keep `qbob_state/deployment_id`: without it NekroAgent no longer recognises the bots it created.
- Knowledge-base indexing runs at most 2 jobs at a time per queue (`KB_INDEX_CONCURRENCY`, upstream uses 3), because each job keeps a whole document's vectors in memory; raise it on hosts with more memory.

### Known gaps
- `install_i18n.sh` and `wrtinstall.sh` have no `--with-qbob` option; use `install.sh` to set up qbob.
- The email plugin reads the mailboxes configured at platform level, and the emotion library is one store shared by everyone; neither has a per-tenant owner. If you host several tenants, leave both plugins off for tenants you do not trust.
- The CC workspace and GitHub plugins still hand their results and webhook content to the AI as system messages. If you host several tenants, leave them off for tenants you do not trust, and subscribe only to repositories you control.
- Reading videos from the local disk is only available for NapCat instances created in the console. The NapCat from `docker-compose-x-napcat.yml` counts as a remote endpoint, so only its links are used.

## v0.3.0 (2026-11-01)

### Added
- **Built-in plugin "Video Analysis"**: the AI can read and analyze videos. The new sandbox method `analyze_video(source, question)` takes a video from the chat, a sandbox path or an http(s) link, samples frames with `ffmpeg`, sends them to a vision model group in batches and returns the answer. Optionally, the audio track is sent to an OpenAI-compatible transcription endpoint (off by default, because the audio leaves your host). The plugin is off by default; enable it in the plugin page and pick a vision model group, or leave `VIDEO_MODEL_GROUP` empty to use the channel's primary or fallback group when it has vision.
- Conservative limits with hard ceilings: 64 MB, 10 minutes, 16 frames, 768 px long edge, 8 frames per request, 100 seconds in total, 2 concurrent jobs process-wide and 1 per instance. An instance can tighten these but not loosen them (the one exception is frames per request: smaller batches mean more requests, so an instance can only raise it); an instance cannot turn on scene detection or audio transcription while they are off globally. The total time is also capped at the sandbox timeout minus 10 seconds, so raise `SANDBOX_RUNNING_TIMEOUT` if you raise it.
- Video content is treated as untrusted: links go through the existing outbound protection on every redirect, and the actual peer is checked again after connecting. `ffmpeg` only reads local plain video containers from an isolated working directory that is always removed afterwards, with memory limits and its whole process tree killed on timeout. Text from the video or the models is sanitized, marked as untrusted, and not stored as a system message. Every upstream request appears in the usage ledger under the `plugin` scene.
- New `UntrustedToolResult` for plugin authors: return it from a sandbox method to hand external content to the model without it becoming a system message or passing through the sandbox.

### Security
- The outbound URL check now refuses IPv6 forms that lead to IPv4 ranges or are deprecated (`::/96`, `64:ff9b::/96`, `64:ff9b:1::/48`, `2002::/16`, `fec0::/10`). This also applies to chat image downloads and tenant endpoints.
- QQ media links are no longer written to logs with their `rkey`, neither in log messages nor in exception text, and log redaction now matches parameter names by whole word (parameters such as `author` or `design` are no longer masked by mistake).
- History lines of messages that are referenced, or shown with message ids, no longer lose the session token: tool results are always wrapped in an untrusted block.
- **`docker-guard` could be bypassed; please update if you use the hardened deployment.** Fixed: bind sources that reach outside the data directory through symbolic links; request bodies whose keys differ only in case from the documented ones; the flat `HostConfig` form of older Docker Engines; request bodies on `start` / `restart`; restart policies on containers with bind mounts; `MaskedPaths` / `ReadonlyPaths`, which unmask `/proc` and `/sys` paths; and several other `HostConfig` fields NekroAgent never sends. Request bodies are now checked against exact-key whitelists and the guard forwards the structure it checked. These fixes have not been exercised against a real Docker daemon yet, only against test doubles. See [`docs/docker-guard.md`](docs/docker-guard.md).

### Changed
- The image now includes `ffmpeg`, which makes it larger. Without Docker, install `ffmpeg` and `ffprobe` yourself if you want the plugin; nothing else depends on them.
- With the plugin on, OneBot video messages are no longer dropped: the model sees `[Video: message:<id>]`, and the link is fetched only when the video is analyzed. With the plugin off, nothing changes, except that a lone video sent in a private chat is still recorded but no longer triggers an empty reply from the AI (before, the synthesized "mention" left in the message did). A recalled video cannot be analyzed.

### Upgrade notes
- **Hardened deployment: add the data directory to the guard sidecar.** In `docker/docker-compose-x-hardened.yml`, `nekro_docker_guard` now needs `- ${NEKRO_DATA_DIR}:${NEKRO_DATA_DIR}:ro` under `volumes`. If you keep your own copy of that file, add this line when you upgrade. Without it the guard refuses every mount under the data directory, so the sandbox, CC workspaces and NapCat will not start.
- **The Video Analysis plugin is off by default and needs `ffmpeg`.** The Docker images include it. Video links are downloaded without any proxy (`HTTP_PROXY` and similar variables are ignored), so a host that can only reach the internet through a proxy cannot download links from the chat.
- Hardened deployment: existing NapCat containers are switched to the restart policy `no` at start-up and kept alive by NekroAgent instead. If that migration fails, the log names the container; delete and re-create it from the console.

## v0.2.0 (2026-10-31)

First public edition. It is exported as a whole from the maintainers' development repository, so there is no per-commit history here; this entry summarizes what the
edition contains compared with upstream `2.3.3`. The authoritative statement of modifications is `NOTICE` ("Statement of changes") together with this file; to identify exactly which files differ, compare this tree with the upstream `2.3.3` release.

### Added
- Multi-instance operation (one process, several logical bot instances), a platform console, and three-level permissions (platform operator / tenant admin / read-only member).
- Identity and favourability: memory-domain based isolation of favourability and memory, identity alias requests with an approval flow, joining an instance to a memory domain with the existing favourability folded in, and a soft reply gate that makes a bot less eager to reply unprompted to people it has a low favourability with.
- LLM usage ledger: one row per upstream request, aggregated by instance, tenant and model group (`/console/usage`).
- Model-group API keys are encrypted at rest; a startup audit warns about example, placeholder, short or duplicated JWT signing keys, a weak admin password and a factory-default database password.
- Optional `docker.sock` hardening (`docker/docker-compose-x-hardened.yml`, [`docs/docker-guard.md`](docs/docker-guard.md)) and a short operations guide ([`docs/operations.md`](docs/operations.md)).
- Database migrations 15 to 26 add the tenant / model-group, favourability, identity-scope, memory-persona, usage-ledger, identity-alias-request, password-generation and uniqueness tables, columns and indexes. Apply them in order.

### Changed
- **Container images are published to this edition's GHCR namespace** (`ghcr.io/akiyo-dayo/nekro-agent-byakiyo` and `ghcr.io/akiyo-dayo/nekro-agent-byakiyo-sandbox`; the packages are public and can be pulled anonymously) by workflows that use only the built-in `GITHUB_TOKEN`. The two inherited PyPI publish jobs are disabled.
- The installers (`docker/install.sh`, `install_i18n.sh`, `wrtinstall.sh`) generate random JWT signing keys, keep an existing compose file from this edition and otherwise download it (and `.env.example`) from this repository's `main` branch instead of the upstream one, and no longer make the data directory's `.env` or the credential master key readable by every account.
- Rotating `NEKRO_ADMIN_PASSWORD` now invalidates previously issued admin tokens; `NEKRO_SUPER_ACCESS_KEY` now actually takes effect when set.
- Both Dockerfiles point apt at `archive.debian.org` because the Debian 11 (bullseye) base image's packages are gone from the regular mirrors.

### Fixed
- Several security and robustness fixes found during review: credentials leaking through logs and upstream error text, tenant-visible endpoints that should have been platform-only, concurrent first-message user creation producing duplicate rows, and read-only members seeing an empty page where they should see a "no access" message.
- `backend-tests.yml` was an invalid workflow file (duplicate `NO_PROXY` / `no_proxy` keys in `env`); two tests that only passed on Windows by accident now pass on Linux as well.

### Documentation
- `README.md`, `README_en.md` and `NOTICE` state that telemetry and the NekroAI cloud service are **on by default** (inherited from upstream, behaviour unchanged), what is reported, and how to turn it off, including a known limitation of the switch when no cloud API key is configured.
- The user interface now shows "Built on the NekroAgent project" with a clickable link to the upstream project (login page and sidebar footer).

### Compatibility and deployment notes
- Upgrading from an earlier build: the first start after the upgrade signs everybody out once if you let the installer write JWT keys for a Docker deployment; admins sign in again after a password rotation.
- The new default sandbox image name only applies to newly generated configuration; set `SANDBOX_IMAGE_NAME` yourself on an existing deployment.
- Back up the model-group credential key material (the `NEKRO_CREDENTIAL_SECRET_KEY` environment variable or `credential_secret.key`) separately from database backups; without it the stored API keys cannot be decrypted.
