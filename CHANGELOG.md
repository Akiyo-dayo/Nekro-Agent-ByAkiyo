# Changelog

Version numbers here are this derivative edition's own (`FORK_VERSION` in `nekro_agent/tools/common_util.py`). This edition is based on upstream
NekroAgent `2.4.0` (`UPSTREAM_BASE_VERSION`; up to v0.4.2 it was based on `2.3.3`). The `version` in `pyproject.toml` is the plugin-compatibility version (`2.4.0`): plugins written for that
upstream version install and run here. It drives plugin-compatibility checks and update checks, and is not this edition's own version.

## v0.4.3 (2026-11-03)

Bug fixes, a cross-tenant OneBot account takeover fix, a way to change an instance's access token, two security fixes in the MCP server test, a prompt-injection fix for the CC workspace and GitHub plugins, fixes for status-mail flooding, the quota whitelist and plugin activation, and web chat from upstream 2.4.0. No database migration, no new dependency; the new `web` adapter brings its own adapter settings.

### Security
- **Please update if you host tenants: a tenant could take over an account you were about to bind to your own OneBot instance.** While an account is not bound to an instance, a connection may also present the token of any instance still waiting for an account (or nothing at all when `ONEBOT_ACCESS_TOKEN` is empty). A tenant with the token of its own waiting instance could connect first with your bot's account; after you bound, adopted or claimed the account, that connection stayed, its messages were handled as your instance's messages, your real protocol endpoint was refused as a duplicate, and what NekroAgent sent to the account went to the tenant. A connection now counts for an account only if the token it presented is the one the account's instance currently requires: when an account binding changes, connections that no longer match are closed, and messages arriving on such a connection are dropped.
- An HTTP-reported event for an account that was not bound yet could keep that account's WebSocket endpoint refused as a duplicate until restart. A WebSocket that passes the token check now takes the account over from such a leftover.
- **Incoming attachment names could write files outside the upload directory (affects v0.4.2 and earlier).** With the QQ official bot adapter (`qqbot_openclaw`), the name of an incoming attachment was used as it was when the file was saved, so a name containing `../` or an absolute path could put the file outside the upload directory, for example into the plugin directory. This path is reachable in the code; whether QQ's servers let such a name through has not been verified. File names are now reduced to a single plain file name, and the target must still lie inside the upload directory. The new WeChat OpenILink media support in this release is covered as well.
- **A tenant could run commands in another workspace's sandbox through the MCP test button.** Testing a stdio MCP server in a workspace whose container had never been started fell back to any running workspace. A test for a given workspace now only runs in that workspace's own container.
- **The MCP test that tenants can use connected from the server to any address.** For tenant accounts, http and sse MCP servers are now tested only on public addresses (no loopback, private, link-local or cloud metadata addresses), redirects are not followed, and every request and the actual peer of every response are checked again. A refused address is reported as "address not allowed" without connecting. Tests run by the platform operator are not restricted.
- **Text from the CC workspace and from GitHub webhooks could act as system instructions.** CC's results and error messages, the stored description of a delegated task, and the titles, bodies and comments of issues and pull requests in a subscribed GitHub repository were pushed into the conversation as system messages, which the model is told to trust, and triggered the agent at once. Anyone who can open an issue on a subscribed repository, or influence what CC reads (workspace files, web pages), could inject instructions this way. This text is now stored and shown to the model as untrusted content, wrapped like other tool results; only the plugin's own notice stays outside (with the workspace name, repository and event name quoted on one line). The agent is still triggered as before. Issue and pull request titles are folded into one line.
- **Bot status mails could flood your mailbox.** With status mails turned on, every OneBot connect and disconnect sent a mail, also for anonymous protocol endpoints that registered as unclaimed instances while `ONEBOT_ACCESS_TOKEN` was empty, so anyone could connect and disconnect again and again. Mails now go out only for claimed instances that are in service (not unclaimed, disabled, archived, deleted or belonging to a suspended tenant), at most 4 per bot and 20 in total per 30 minutes; the count survives restarts, and the last mail of a window says so.
- **The quota whitelist trusted any sender ID.** The same number on another platform, an SSE caller's `from_id`, an email sender or a number reported by a tenant's own protocol endpoint skipped the reply quota. The whitelist now works like `SUPER_USERS`: bare numbers are QQ numbers, other platforms use `adapter:ID`, and only sources you control count.
- **Plugins switched off for an instance or chat could still be activated.** The plugin-activation helper returned the full description (methods and injected context) of a sleeping plugin switched off for the current instance or chat. It now only sees the plugins that chat can use.

### Fixed
- **Messages from people with a QQ coloured or special group card could be lost on PostgreSQL.** Some protocol endpoints (for example SnowLuma) report such a card as raw bytes that end in a NUL character, which PostgreSQL refuses, so the whole message was dropped. NUL is now removed before anything is saved. Nicknames, group cards and group names from OneBot also have control characters removed when they arrive, which gives the same name NapCat reports for the same card. A sender whose nickname and card are both empty after cleaning is shown by QQ number instead of the message being dropped.
- With `SESSION_ENABLE_AT` turned off, @-mentions in multi-instance OneBot chats find the right group again.
- Config files are written atomically: a write cut short (full disk, killed process) can no longer leave a truncated file that stops NekroAgent from starting.

### Added
- **Change an instance's access token.** On a OneBot instance's page the platform owner can generate a new access token. The old one stops working at once and connections to the instance that used it are closed; a running built-in NapCat gets the new configuration and restarts (a disabled instance or a stopped container only gets the configuration), a built-in qbob bot is rewired, and for a remote endpoint the page shows the new token to copy into its configuration. An instance whose token a tenant had (for example one you recalled from a tenant) is a trusted super-user source again with the new token.
- **Web chat** (from upstream 2.4.0): the platform operator can talk to the bot directly from the console ("Chat management → Web chat"), with sessions, text and single-file messages. Messages go through the normal pipeline, including plugin hooks and commands. Only the platform operator can use it: tenant accounts get 403 and do not see the menu, the pages or the sessions.
- **Web Chat MCP** at `/api/mcp/web-chat/mcp`: MCP clients can create web chat sessions, send messages, wait for replies and read history. It accepts the platform operator's console login or an optional fixed key (off by default, stored only as a hash). **Unlike upstream 2.4.0, workspaces do not get a web chat MCP key in this release:** a workspace's owner follows the channels bound to it, and a key written into a workspace could reach a tenant and later be used as the platform operator, so workspace coding agents cannot use web chat MCP for now. From your own MCP client, use the fixed key, and do not put it into a workspace's own configuration.
- MCP library: "Add from template".
- The channel page can refresh the channel name from the platform; if that fails, the stored name is kept.
- WeChat OpenILink: incoming images and files are saved like on other adapters.

### Changed
- **This edition is now based on upstream NekroAgent 2.4.0** (it was based on 2.3.3 and plugin-compatible with 2.4.0). Every upstream change up to 2.4.0 is included; a few were adapted to this edition's multi-tenant rules instead of being taken as they are: web chat is for the platform operator only and its MCP endpoint gives no key to workspaces in this release (see Added), the email body XSS protection uses a sandboxed frame instead of DOMPurify, and a WeChat iLink database fix is done by this edition's own migration. `NOTICE` and the README now name 2.4.0 as the version to compare this tree with.
- `.mcp.json` in workspaces uses the `type` key that Claude Code expects instead of `transport`.
- Saving the global MCP library resets an entry to "unvalidated" when its connection settings change.
- The web adapter setting "treat WebUI admin as command super user" (off by default) only applies to the platform operator's super-admin accounts.

### Upgrade notes
- Moving or claiming an account onto an instance that requires a different token than the one its endpoint uses closes the old connection at once; a remote endpoint has to use the new instance's token to reconnect.
- If you recalled an instance from a tenant, change its access token on the instance page so that super-user chat commands work there again.
- The web adapter is on by default (setting "Enable web adapter"; restart to apply). A web chat entry you added to the global MCP library by hand is no longer written into workspaces, and its headers are cleared.
- For plugin authors: an `on_system_message` hook only sees the plugin's own notice for CC workspace results and GitHub events, not the external text. To push external content yourself, use `message_service.push_untrusted_message(chat_key, UntrustedToolResult(...), trigger_agent=...)` instead of `push_system_message`.
- Check your quota whitelist (`AI_CHAT_QUOTA_WHITELIST_USERS`): a bare number now only matches a QQ number, so write users of other platforms as `adapter:ID` (for example `telegram:123456`). Entries do not apply in tenant instances, unclaimed instances, or on adapters such as SSE and email where the caller supplies the sender ID.
- Bot status mails are capped at 4 per bot and 20 in total per 30 minutes and are not sent for unclaimed or switched-off instances; the count is kept in `data/system`.

## v0.4.2 (2026-11-03)

**Security release: please update.** This is the first public release since v0.3.0. Versions 0.3.1, 0.4.0 and 0.4.1 were not published on their own; everything they contain is included here. Updating from v0.3.0 fixes, among other things (details under Security):

- Stored cross-site scripting: an email to the bot's mailbox, or HTML in a chat message, plugin document or announcement shown in the console, could run script as the logged-in admin.
- Code running in the sandbox could run arbitrary code inside the NekroAgent process.
- Chat-command super users could be impersonated, so a tenant, an anonymous protocol endpoint or a caller of the SSE adapter could run shell commands through the bot.
- With an empty `ONEBOT_ACCESS_TOKEN`, any OneBot endpoint that connected could use the bot and your model quota.
- Image and file downloads, and model endpoints entered by tenants, could reach the server's internal network through certain international host names.
- Several ways for one tenant to read or change another tenant's channels, instances, timers or chat history.

This edition is still based on NekroAgent 2.3.3 and is now plugin-compatible with 2.4.0. It includes most of upstream 2.4.0's features and fixes (knowledge-base batch operations and zip import, plugin call priority, command permissions and channel scope, WeChat iLink fixes and others); upstream 2.4.0's web chat adapter and MCP online test are not included yet.

Some of these fixes change behaviour. Read the upgrade notes before updating, especially if `ONEBOT_ACCESS_TOKEN` is empty, if you use `SUPER_USERS`, or if you host tenants.

### Security
- **Please update: an email or a chat message could run script in the console as the logged-in admin.** The email viewer injected the HTML body into the page, and the Markdown renderer used for chat history, email `.md` attachments, plugin docs, skills and announcements rendered raw HTML without filtering. Email bodies are now shown in a fully sandboxed frame with a strict content security policy (no scripts, forms, popups or self-navigation), and Markdown no longer renders raw HTML except in the bundled adapter docs.
- A late "unauthorised" answer to a request made with an old login no longer logs out a session that was just created.
- Plugin web pages only serve web assets (HTML, scripts, styles, images, fonts, JSON, WebAssembly, media); plugin source files, databases and configuration files are never served.
- **Please update: code running in the sandbox could run arbitrary code inside the NekroAgent process.** The sandbox's plugin-call endpoint decoded request bodies with `pickle`, and sandbox code can read the callback token it needs. Requests from the sandbox are now plain JSON with explicit type tags, decoded only after the token has been checked; NekroAgent rebuilds tagged values with fixed constructors and never looks up a class or function named in a request. Answers to the sandbox are checked against a whitelist before they are sent, and the sandbox decodes them with the same whitelist.
- Requests from the sandbox are limited: 1 MiB per call, plus limits on nesting, number of values and containers, string and integer length, on how many calls one sandbox can have in transit or running at once, and on how much decoding time it can use per second. Requests are decoded one at a time. This limits how much a busy or hostile sandbox can slow other conversations down. Calls refused because the server is busy are retried automatically; oversized or malformed requests come back to the sandbox as an error instead of tying up the server.
- Methods whose result the AI reads as a system message no longer repeat their arguments verbatim: echoed arguments are shortened to one line, quoted, and stripped of invisible characters. Invisible characters that can hide text are also removed from untrusted content, while emoji sequences, flags and scripts that need joining characters (such as Persian and Devanagari) are kept intact.
- **A sandbox method can no longer reach another channel's or another tenant's data by passing its `chat_key`.** `find_history_travel` / `find_history_travel_range` (chat history), notes and character status now accept only the current session and answer exactly as if the channel did not exist. The range search also no longer follows a message ID that belongs to another channel.
- Timers (including recurring timers, whose 4-character `job_id` could be guessed), sending messages, AI voice, group titles, Minecraft rich text and RCON, the Bilibili live methods, forwarding an email attachment and `draw(send_to_chat=...)` work for channels of the same tenant and are refused across tenants. In a deployment where no instance belongs to a tenant (the default), every channel stays reachable as before, including Telegram chats.
- **Content from outside no longer comes back to the model as a system message.** Search results, emails, chat history, knowledge-base and memory results, RCON output, skill documents and the skill list, CC collaboration context, `view_str_content` and `view_image` descriptions are returned as `UntrustedToolResult`: stored as a tool-result row, wrapped in an untrusted block with the token of the turn that reads it, and never passed back through the sandbox. Plugins that return a plain string keep the old behaviour.
- Long history lines are cut inside the untrusted block instead of across it, so the block's tags are never lost. `view_str_content` returns at most 16000 characters per call.
- Video files on the local disk are only read for the built-in NapCat that NekroAgent itself started, only inside that instance's data directory and only if they are video files; a remote protocol endpoint cannot make NekroAgent read local files. A file fetched through `get_file` is used only if its name and size match the chat record, because NapCat's `get_file` looks files up by name.
- A video playback address stops working at once when its user is banned, loses Admin rights, leaves the tenant or changes their password.
- Video streaming has limits: 6 streams per user and 32 in total, with at most 8 per tenant; every tenant keeps 2 for itself and the last 8 are never handed out beyond those guaranteed shares, so busy tenants cannot lock out the others or the platform. There is also a 60-second timeout for a browser that stops reading and a 64 MB seek limit on sources that do not support Range. A stream cut by these limits, or by the 512 MB size cap, ends as an interruption, never as a complete (truncated) video.
- An anonymous request whose path contains `<`…`>` can no longer turn into a server error when debug logging is on.
- A forged video playback address is refused without a database lookup; a malformed one can no longer cause a server error.
- On a Windows host, a path reported by NapCat that names another drive or a network share is refused before any file lookup, so no connection to that share is made. The real path of an opened file is taken from the file handle, not from a `/proc` path that on Windows would point into the root of the drive.
- **A tenant could reach another tenant's instance through a same-named instance of another adapter.** Instance keys are only unique within one adapter, but tenant checks compared the key alone. Checks and filters now use the adapter and the key together, new instances can no longer take a key another adapter already uses, and NekroAgent logs a warning at startup for each key that existing data already shares.
- WeChat iLink multi-instance management had no tenant check, and a few adapter maintenance endpoints that act on the whole deployment (`qqbot_openclaw`, the `wechat_openilink` login status) were open to tenant admins. They are now limited to the platform owner; tenants only see and manage their own WeChat instances.
- Per-instance plugin credentials are redacted before a sandbox method's result or error goes back to the sandbox, like global ones.
- Knowledge-base zip import treats the archive as untrusted: absolute paths, drive letters, `..` and control characters reject the whole archive; file and total sizes are limited by the bytes actually written, not only by what the archive declares; only stored and Deflate entries are accepted; symlinks and macOS metadata are skipped; extraction runs off the event loop, at most two imports at a time.
- **Moving an instance to another tenant, or disabling it, could be undone by the next WeChat iLink session renewal or instance health check**, which saved the whole instance as it had read it earlier. Status updates and renewals now only write their own fields, so tenant assignment, the enabled switch, the bound account and the name stay as the platform admin left them.
- **A disabled, archived or deleted instance could be switched back to a running state by its own connection, a session renewal or the health check**, and a deleted instance revived this way could hold the same account as another instance. Automatic status updates now only apply while the instance is enabled and not disabled, archived or deleted; only the platform admin can bring an instance back.
- **Please update: chat-command super users could be impersonated.** Anyone whose user ID was listed in `SUPER_USERS` counted as a super user on every adapter and through every source, so a tenant's own OneBot protocol endpoint, an anonymous endpoint that connected while the deployment token was empty, or a caller of the SSE adapter could present a listed number and run shell commands; tenants could also read the list. A super user now needs a list entry for the right platform and a trusted source. Plain numbers are QQ numbers on OneBot; other platforms use `adapter:ID`. Adapters whose sender ID is filled in by the caller or a relay (SSE, email, Bilibili live, Minecraft, wechatpad) never count. OneBot counts only on a claimed platform instance whose token has never been visible to a tenant, and only for messages on a connection that presented that instance's current token. NekroAgent keeps fingerprints of tokens that tenants have had; if that record is lost or damaged it is rebuilt before the next check, and until then no OneBot super user is accepted. Moving an instance between the platform and a tenant is refused while that record cannot be written. `SUPER_USERS` is hidden from tenants, also in the channel's effective settings, and only the super admin can change it or reset the system settings.
- **Image and file downloads, and the model endpoints tenants enter, could reach the server's internal network through a host name with certain international characters** (such as `ß`), because the check and the connection spelled that name differently. The check now looks up exactly the host that is connected to.
- Downloads no longer accept compressed bodies, which could expand far past the size limit in memory before the limit was checked.
- **Please update: with an empty `ONEBOT_ACCESS_TOKEN`, anyone could use the bot.** An unknown OneBot endpoint that connected was registered as an unclaimed instance and its messages, notices and commands were processed, using your model quota. Messages of an unclaimed instance are now processed only if its connection presented your current deployment token (and no tenant has had that token). Connections are still accepted, so you can claim them in the console; once claimed, an instance works as before without reconnecting.

### Fixed
- **Plugins from the upstream NekroAgent market that wrap the command hook (such as novelai) no longer stop every channel from receiving messages.** Plugins written for upstream 2.4.x now install and run here; a plugin that replaces a framework function with a wrong signature only loses its own extra feature, with a warning in the log.
- WeChat iLink multi-instance: a successfully bound instance can start and receive messages again; deleting an instance stops its connection; disabling and re-enabling an instance resumes it at once.
- WeChat iLink multi-instance: binding or renewing an instance from two places at once could leave it with two sessions, after which it would not start. Each instance now has exactly one session, and a connection that is still running during a rebind can no longer write back old credentials or an old sync position.
- The console checks that your login is still valid before showing the main pages, and an expired login redirects to the login page once.
- The draw plugin works with models that return images in the plural `images` field.
- Editing a Gmail or Outlook account keeps its connection type, and the connection type can be chosen.
- Mobile layout of the console; the elapsed time on activity cards is never negative.
- OneBot videos no longer disappear when the video plugin is off. A video now always appears in the chat history. With the plugin off the AI knows a video is there and tells the user it cannot watch it, instead of saying nothing was sent.
- Replying to a video points the AI at that video, even when it is no longer in the recent context.
- When a video link is missing or expired, the plugin falls back to `get_file` and, on the built-in NapCat, to the local file. If everything fails the error says why.
- The WebUI player also works with storage that labels videos as generic binary data and supports Range requests.
- AI voice messages sent by NekroAgent are no longer recorded a second time as messages from another program.
- The video placeholder no longer trips keyword triggers or ignore rules, and a video sent with text containing `(id:` is no longer dropped.
- OneBot messages that hold only a face, sticker, dice, poke or another segment NekroAgent does not handle are no longer dropped: they appear in the chat history with a short placeholder. Images or files that cannot be fetched or are too large leave a placeholder too, and forwarded messages keep their videos, voice messages and files as placeholders. Placeholders never contain text the sender chose.
- Sandbox methods, timers and adapters other than OneBot now use a plugin's per-instance settings instead of the global ones.
- Purging an instance no longer deletes the chats of a same-named instance of another adapter; while such a name clash exists, purging is refused.
- The built-in NapCat connects to the port NekroAgent listens on, so deployments with a non-default `NEKRO_EXPOSE_PORT` no longer stay offline, and the sandbox callback address follows a changed port.
- Rebuilding a knowledge-base document keeps the previous index searchable until the new one is committed in a single database transaction; a failed or cancelled rebuild leaves the old index as it was.
- Concurrent uploads of identical content to the knowledge-base library reuse the existing entry and leave no orphan file.
- OneBot group messages are no longer dropped when looking up the sender's group card fails (the protocol endpoint times out, or the member has left the group): the name falls back to the card or nickname carried by the message, or to the QQ number.
- OneBot videos whose message number is negative (about half of them on NapCat and SnowLuma) now play in the WebUI, can be analysed by the AI and are recognised when someone replies to them. Before, they always showed "this video cannot be played right now".
- QQ custom and super stickers, which the QQ server delivers through a redirect, no longer turn into an "image unavailable" placeholder. Image and file downloads follow up to 3 redirects, and every redirect target goes through the same check as the original link (http / https only, public addresses only); the size limit applies after redirects as before.

### Added
- **Plugin compatibility with upstream NekroAgent 2.4.0**, including plugin web pages (`webui_path`): plugins that ship a web page get a WebUI tab in plugin management. Market plugins that require NekroAgent 2.4.0 can be installed.
- **Plugin call priority** (from upstream 2.4.0): in plugin management the platform owner can mark a plugin auto, high, medium or low. When several plugins can do the same job, the AI tries the higher tier first and falls back to the next one if it fails. The setting applies to the whole deployment; tenants can see it but not change it.
- **Knowledge-base batch operations and zip import** (from upstream 2.4.0): batch delete, unbind and reindex are single backend calls, batch upload no longer waits for indexing, and a zip archive can be imported with its folders as categories (Chinese file names from archives without the UTF-8 flag are read correctly). In the shared library these are limited to the platform owner like their single-item versions; in a workspace they follow the workspace's tenant scope. New settings `KB_INDEX_CONCURRENCY`, `KB_BATCH_MAX_SIZE`, `KB_BATCH_CONCURRENCY`, `KB_ZIP_MAX_UPLOAD_SIZE_MB`, `KB_ZIP_MAX_EXTRACT_SIZE_MB`, `KB_ZIP_MAX_FILES`.
- **Built-in qbob for QQ official bots.** [qbob](https://github.com/Loping151/qbob) (AGPL-3.0) can run next to NekroAgent as a separate container (`install.sh --with-qbob`), built on your host from a pinned upstream commit. Connect a bot from the console by scanning the QQ open-platform code or entering its AppID and AppSecret; tenants can watch, switch and reload their own bots. NekroAgent does not include qbob's code. See `docs/qbob-integration.md`.
- **Messages from other programs on the same account.** When another framework shares the protocol endpoint with NekroAgent, its messages are now recorded and visible to the AI, marked as coming from the same account. They never trigger a reply, a command, a quota or affection change, so two frameworks cannot trigger each other in a loop. NekroAgent's own messages are filtered out by message id. Setting: `ONEBOT_RECORD_SELF_SENT` (on by default, can be overridden per channel).
- **Video player in the WebUI.** Chat videos play inline with seeking, through a short-lived signed address tied to the message, channel and user. It works without the video plugin; links are fetched on demand and never stored.
- **Model group names can use Chinese, Japanese and Korean**, plus spaces and common punctuation between characters. Look-alike letters (Cyrillic, Greek, full-width Latin) and invisible characters are still refused. Existing groups stay editable even if their names predate the rule.
- **Batch delete for model groups**, and a warning before deleting a group that configs still use (it only warns, it does not block).
- **Channel admins for chat commands** (from upstream 2.4.0): a channel admin can use `reset`, `stop`, `na_on`, `na_off` and `na_observe` in its own channel only; other channels and "all channels" still need a super user. The platform owner can make someone a channel admin everywhere (`grant_advanced` / `revoke_advanced`); a tenant admin can do it for one of its own channels in the channel's new "Command permissions" tab. Group owners and admins become channel admins automatically only where `COMMAND_GROUP_ADMIN_AS_CHANNEL_ADMIN` is turned on (off by default, can be set per instance or channel; upstream always does this). Super users are still exactly the ones in `SUPER_USERS`. User management and the channel user list show each user's command permission.
- **The console shows which OneBot protocol endpoint an instance uses and whether it reports the account's own messages.** The instance's protocol tab names the implementation and version (SnowLuma, NapCat or another). NekroAgent cannot ask the endpoint whether self-message reporting is on, so it checks whether its own messages come back: when several in a row do not, the page says the setting is probably off, explains where to turn it on in SnowLuma or NapCat, and the log says so once. It notices when the setting is switched off without a reconnect, too. Tenants see this for their own instances.
- **Cold shoulder plugin (off by default).** The AI can decide to ignore one person in the current chat for a while, for example someone who keeps poking it after it said it would stop answering: that person's messages and pokes are still recorded but no longer wake the AI up. Everyone else in the chat, other chats and other bot accounts are unaffected, and chat commands keep working. The AI picks the duration, up to `MAX_MINUTES` (120 minutes by default, can be set per instance); it can only pick someone who spoke in the chat in the last few minutes, and super users are never ignored. The list shows up under the channel's "Plugin data", where it can be edited or cleared, and is emptied when the channel is reset. Turn the plugin on in plugin management.

### Changed
- `exec`, `sh`, `docker_restart`, `docker_logs` and the `conf_*` commands now need a super user; `reset`, `stop`, `na_on`, `na_off` and `na_observe` need a channel admin and only act on the current channel unless a super user runs them.
- The `version` in `pyproject.toml` is now the plugin-compatibility version `2.4.0`; this edition is still based on upstream `2.3.3`. The sidebar shows this edition's own version; `/na_info` and `/na_help` show both.
- CC workspace: letting the AI create a workspace and letting it start a stopped sandbox are two separate settings. Existing configurations keep what they allowed before.
- **Plugin authors, arguments:** sandbox methods can receive `None`, `bool`, `int`, `float`, `str`, `list`, `tuple`, `dict`, `set`, `frozenset`, `bytes`, `datetime` / `date` / `time` / `timedelta` and `UUID`, up to 1 MiB of encoded arguments per call. `pathlib.Path` arrives as `str`, `OrderedDict` as `dict`, `bytearray` as `bytes`, enum values as their plain value. `Decimal`, `complex`, custom classes, `numpy` integer scalars and `pandas` objects fail in the sandbox with an error that names the type and the argument; convert them first (`str()` / `float()` / `.item()`). Calls over a limit (1 MiB, 32 levels of nesting, 100000 values, 10000 lists / dicts, 1,000,000-character strings, 768 KiB of bytes, 100-digit integers) also fail in the sandbox before anything is sent; the message says which argument and how to shrink it. Both cases raise `RpcArgumentError` (a `TypeError` and a `ValueError`), and a call NekroAgent refuses before running it raises `RpcRejectedError` (a `RuntimeError`); code in the sandbox can catch either instead of the run ending. A call refused only because the server is busy is retried automatically for up to 30 seconds before `RpcRejectedError` is raised. Calls from several threads run concurrently, up to 8 at a time.
- **Plugin authors, return values:** the same plain types plus `bytearray`, `complex`, `Decimal`, `OrderedDict` and POSIX paths. Returning a custom class, a `numpy` scalar or a `pandas` object fails with an error that names the type.
- Messages that consist only of a face, sticker, dice or poke can now trigger a reply (private chats, channels set to reply to everything, keyword triggers matching the placeholder).
- The sidebar and login page show the copyright year and "Built on the NekroAgent project" on one line.

### Upgrade notes
- **Back up the database and the data directory before updating.** One database migration runs on the first start (see below).
- **If `ONEBOT_ACCESS_TOKEN` is empty, claim your OneBot instances before updating.** Unclaimed instances no longer have their messages processed unless their connection presented your current, non-empty deployment token. Instances shown as "unclaimed" in the console only keep receiving messages if they already have chat history: those are claimed automatically on the first start (the log lists them; archive any that are not yours). Unclaimed instances without chat history receive nothing until you claim them; the log warns and the console marks them. Instances you created or claimed are not affected. Setting `ONEBOT_ACCESS_TOKEN` is recommended.
- **Super-user chat commands now depend on the connection's token.** Plain QQ numbers in `SUPER_USERS` keep working on your own OneBot instances that have their own token, or that use a non-empty `ONEBOT_ACCESS_TOKEN` no tenant has had. Super-user commands no longer work in tenants' bots, in unclaimed instances, with an empty `ONEBOT_ACCESS_TOKEN`, or through SSE, email, Bilibili live, Minecraft and wechatpad; use the console command page there. Write users of other platforms as `adapter:ID`, for example `telegram:123456`. The startup log warns about each of these cases.
- Protocol endpoints reconnect after the restart, which is all they need. After claiming an instance or moving an account in the console, the protocol endpoint must reconnect once more before super-user commands work there.
- If you host tenants and recalled an instance from a tenant before this update, or a tenant instance used the deployment token, change that token (`ONEBOT_ACCESS_TOKEN` takes effect after a restart; instance tokens cannot be changed in the console yet). The startup log lists the instances concerned.
- NekroAgent keeps its record of tokens that tenants have had under `data/system/`. Keep that directory writable: moving an instance between the platform and a tenant is refused while the record cannot be written.
- Plugins that check `SUPER_USERS` themselves still see the plain list and do not know which platform or connection a message came from.
- **Database migration 27** (`27_20261102191729_unique_adapter_instance_session`) is the only one since v0.3.0, which ended at migration 26. It runs automatically on start. It first merges duplicate WeChat iLink sessions (per instance it keeps the one with credentials, then the most recently updated), records the merge in that instance's events, then allows only one session per instance. A downgrade restores the old index but not the merged-away sessions. To check for duplicates beforehand: `SELECT instance_id, count(*) FROM adapter_instance_session GROUP BY 1 HAVING count(*) > 1`.
- **Plugins: compatibility with upstream 2.4.0.** The `version` in `pyproject.toml` is now the plugin-compatibility version `2.4.0` (this edition is still based on upstream `2.3.3`). Market plugins that require NekroAgent 2.4.0 become installable; plugins that declare a maximum version below 2.4.0 can no longer be installed, as on upstream 2.4.0. There is no new dependency.
- Sandbox method arguments are no longer sent with `pickle`. Sandbox code or plugins that pass `Decimal`, `complex`, custom classes, `numpy` integer scalars or `pandas` objects to a sandbox method now get `RpcArgumentError` and have to convert them first (see Changed).
- Command permission overrides you set to "advanced" before this update are changed to "super user" on the first start, because until now only super users could use "advanced"; the log lists every changed entry. Set them again if channel admins should use those commands. Plugin commands that declare "advanced" become usable by channel admins. `ENABLE_ADVANCED_COMMAND` stays off by default (upstream 2.4.0 turns it on).
- Timers created before this update are kept and keep firing. If you host several tenants, open the timer page as the platform admin after updating and remove timers that one tenant's bot set on another tenant's channel; their description usually gives them away. Single-tenant deployments have nothing to check.
- Built-in NapCat: restart each NapCat container once from the console, so that `reportSelfMessage` takes effect and, on a non-default `NEKRO_EXPOSE_PORT`, the connection uses the right port.
- Remote protocol endpoints: turn on `reportSelfMessage` for the connection to NekroAgent yourself, otherwise other programs' messages stay invisible. Nothing breaks if you do not. On SnowLuma, open the account's OneBot settings in its WebUI, turn on "report self messages" on the reverse WebSocket node that points to NekroAgent and save; it applies at once, without a restart or reconnect. The instance's protocol tab in the console shows whether it works. Messages from other programs on the same account are recorded by default; turn off `ONEBOT_RECORD_SELF_SENT` if you do not want them in the chat history.
- If `SANDBOX_CHAT_API_URL` is exactly `http://host.docker.internal:<port>/api` and the port is not the one NekroAgent is published on (in Docker, `NEKRO_EXPOSE_PORT`), it is corrected on start and the log names the old and new value. If that port deliberately points at another service on the host, such as a reverse proxy, write the host gateway IP or another host name instead.
- If startup logs a warning that an instance key is used by more than one adapter, those instances share presets, plugin settings and memory. Rename or remove one of them.
- qbob is opt-in. When you upgrade by hand, use `docker compose pull --ignore-buildable` (the qbob image is built locally), then `docker compose up -d`. Keep `qbob_state/deployment_id`: without it NekroAgent no longer recognises the bots it created.
- Knowledge-base indexing runs at most 2 jobs at a time per queue (`KB_INDEX_CONCURRENCY`, upstream uses 3), because each job keeps a whole document's vectors in memory; raise it on hosts with more memory.

### Known gaps
- `install_i18n.sh` and `wrtinstall.sh` have no `--with-qbob` option; use `install.sh` to set up qbob.
- The email plugin reads the mailboxes configured at platform level, and the emotion library is one store shared by everyone; neither has a per-tenant owner. If you host several tenants, leave both plugins off for tenants you do not trust.
- The CC workspace and GitHub plugins still hand their results and webhook content to the AI as system messages. If you host several tenants, leave them off for tenants you do not trust, and subscribe only to repositories you control.
- Reading videos from the local disk is only available for NapCat instances created in the console. The NapCat from `docker-compose-x-napcat.yml` counts as a remote endpoint, so only its links are used.

## v0.3.0 (2026-11-01)

### Added
- **Built-in plugin "Video Analysis"**: the AI can read and analyze videos. The new sandbox method `analyze_video(source, question)` takes a video from the chat, a sandbox path or an http(s) link, samples frames with `ffmpeg`, sends them to a vision model group in batches and returns the answer. Optionally, the audio track is sent to an OpenAI-compatible transcription endpoint (off by default, because the audio leaves your host). The plugin is off by default; enable it in the plugin page and pick a vision model group, or leave `VIDEO_MODEL_GROUP` empty to use the channel's primary or fallback group when it has vision.
- Conservative limits with hard ceilings: 64 MB, 10 minutes, 16 frames, 768 px long edge, 8 frames per request, 100 seconds in total, 2 concurrent jobs process-wide and 1 per instance. An instance can tighten these but not loosen them (the one exception is frames per request: smaller batches mean more requests, so an instance can only raise it); an instance cannot turn on scene detection or audio transcription while they are off globally. The total time is also capped at the sandbox timeout minus 10 seconds, so raise `SANDBOX_RUNNING_TIMEOUT` if you raise it.
- Video content is treated as untrusted: links go through the existing outbound protection on every redirect, and the actual peer is checked again after connecting. `ffmpeg` only reads local plain video containers from an isolated working directory that is always removed afterwards, with memory limits and its whole process tree killed on timeout. Text from the video or the models is sanitized, marked as untrusted, and not stored as a system message. Every upstream request appears in the usage ledger under the `plugin` scene.
- New `UntrustedToolResult` for plugin authors: return it from a sandbox method to hand external content to the model without it becoming a system message or passing through the sandbox.

### Security
- The outbound URL check now refuses IPv6 forms that lead to IPv4 ranges or are deprecated (`::/96`, `64:ff9b::/96`, `64:ff9b:1::/48`, `2002::/16`, `fec0::/10`). This also applies to chat image downloads and tenant endpoints.
- QQ media links are no longer written to logs with their `rkey`, neither in log messages nor in exception text, and log redaction now matches parameter names by whole word (parameters such as `author` or `design` are no longer masked by mistake).
- History lines of messages that are referenced, or shown with message ids, no longer lose the session token: tool results are always wrapped in an untrusted block.
- **`docker-guard` could be bypassed; please update if you use the hardened deployment.** Fixed: bind sources that reach outside the data directory through symbolic links; request bodies whose keys differ only in case from the documented ones; the flat `HostConfig` form of older Docker Engines; request bodies on `start` / `restart`; restart policies on containers with bind mounts; `MaskedPaths` / `ReadonlyPaths`, which unmask `/proc` and `/sys` paths; and several other `HostConfig` fields NekroAgent never sends. Request bodies are now checked against exact-key whitelists and the guard forwards the structure it checked. These fixes have not been exercised against a real Docker daemon yet, only against test doubles. See [`docs/docker-guard.md`](docs/docker-guard.md).

### Changed
- The image now includes `ffmpeg`, which makes it larger. Without Docker, install `ffmpeg` and `ffprobe` yourself if you want the plugin; nothing else depends on them.
- With the plugin on, OneBot video messages are no longer dropped: the model sees `[Video: message:<id>]`, and the link is fetched only when the video is analyzed. With the plugin off, nothing changes, except that a lone video sent in a private chat is still recorded but no longer triggers an empty reply from the AI (before, the synthesized "mention" left in the message did). A recalled video cannot be analyzed.

### Upgrade notes
- **Hardened deployment: add the data directory to the guard sidecar.** In `docker/docker-compose-x-hardened.yml`, `nekro_docker_guard` now needs `- ${NEKRO_DATA_DIR}:${NEKRO_DATA_DIR}:ro` under `volumes`. If you keep your own copy of that file, add this line when you upgrade. Without it the guard refuses every mount under the data directory, so the sandbox, CC workspaces and NapCat will not start.
- **The Video Analysis plugin is off by default and needs `ffmpeg`.** The Docker images include it. Video links are downloaded without any proxy (`HTTP_PROXY` and similar variables are ignored), so a host that can only reach the internet through a proxy cannot download links from the chat.
- Hardened deployment: existing NapCat containers are switched to the restart policy `no` at start-up and kept alive by NekroAgent instead. If that migration fails, the log names the container; delete and re-create it from the console.

## v0.2.0 (2026-10-31)

First public edition. It is exported as a whole from the maintainers' development repository, so there is no per-commit history here; this entry summarizes what the
edition contains compared with upstream `2.3.3`. The authoritative statement of modifications is `NOTICE` ("Statement of changes") together with this file; to identify exactly which files differ, compare this tree with the upstream `2.3.3` release.

### Added
- Multi-instance operation (one process, several logical bot instances), a platform console, and three-level permissions (platform operator / tenant admin / read-only member).
- Identity and favourability: memory-domain based isolation of favourability and memory, identity alias requests with an approval flow, joining an instance to a memory domain with the existing favourability folded in, and a soft reply gate that makes a bot less eager to reply unprompted to people it has a low favourability with.
- LLM usage ledger: one row per upstream request, aggregated by instance, tenant and model group (`/console/usage`).
- Model-group API keys are encrypted at rest; a startup audit warns about example, placeholder, short or duplicated JWT signing keys, a weak admin password and a factory-default database password.
- Optional `docker.sock` hardening (`docker/docker-compose-x-hardened.yml`, [`docs/docker-guard.md`](docs/docker-guard.md)) and a short operations guide ([`docs/operations.md`](docs/operations.md)).
- Database migrations 15 to 26 add the tenant / model-group, favourability, identity-scope, memory-persona, usage-ledger, identity-alias-request, password-generation and uniqueness tables, columns and indexes. Apply them in order.

### Changed
- **Container images are published to this edition's GHCR namespace** (`ghcr.io/akiyo-dayo/nekro-agent-byakiyo` and `ghcr.io/akiyo-dayo/nekro-agent-byakiyo-sandbox`; the packages are public and can be pulled anonymously) by workflows that use only the built-in `GITHUB_TOKEN`. The two inherited PyPI publish jobs are disabled.
- The installers (`docker/install.sh`, `install_i18n.sh`, `wrtinstall.sh`) generate random JWT signing keys, keep an existing compose file from this edition and otherwise download it (and `.env.example`) from this repository's `main` branch instead of the upstream one, and no longer make the data directory's `.env` or the credential master key readable by every account.
- Rotating `NEKRO_ADMIN_PASSWORD` now invalidates previously issued admin tokens; `NEKRO_SUPER_ACCESS_KEY` now actually takes effect when set.
- Both Dockerfiles point apt at `archive.debian.org` because the Debian 11 (bullseye) base image's packages are gone from the regular mirrors.

### Fixed
- Several security and robustness fixes found during review: credentials leaking through logs and upstream error text, tenant-visible endpoints that should have been platform-only, concurrent first-message user creation producing duplicate rows, and read-only members seeing an empty page where they should see a "no access" message.
- `backend-tests.yml` was an invalid workflow file (duplicate `NO_PROXY` / `no_proxy` keys in `env`); two tests that only passed on Windows by accident now pass on Linux as well.

### Documentation
- `README.md`, `README_en.md` and `NOTICE` state that telemetry and the NekroAI cloud service are **on by default** (inherited from upstream, behaviour unchanged), what is reported, and how to turn it off, including a known limitation of the switch when no cloud API key is configured.
- The user interface now shows "Built on the NekroAgent project" with a clickable link to the upstream project (login page and sidebar footer).

### Compatibility and deployment notes
- Upgrading from an earlier build: the first start after the upgrade signs everybody out once if you let the installer write JWT keys for a Docker deployment; admins sign in again after a password rotation.
- The new default sandbox image name only applies to newly generated configuration; set `SANDBOX_IMAGE_NAME` yourself on an existing deployment.
- Back up the model-group credential key material (the `NEKRO_CREDENTIAL_SECRET_KEY` environment variable or `credential_secret.key`) separately from database backups; without it the stored API keys cannot be decrypted.
