# 运维要点（部署前后的安全与稳定性检查）

这份文档是运行日志里各条告警所指向的说明页，也是上线前建议逐项确认的最小清单。
它只描述**如何配置与自查**，不包含任何具体部署的地址、账号或数据。

**通则**：所有凭据一律**现生成**，不要从文档、示例文件或别的部署抄；生成后不要回贴进工单、聊天记录或任何文档。
推荐命令：`openssl rand -hex 32` 或 `openssl rand -base64 24`。

---

## 1. 凭据与密钥

### 1.1 JWT 两把签名密钥（`NEKRO_JWT_SECRET_KEY` / `NEKRO_JWT_REFRESH_SECRET_KEY`）

这是**最严重的一条**，比后台口令更严重：后端用 `NEKRO_JWT_SECRET_KEY` 签发访问令牌，而鉴权只验签并按 `sub` 回查数据库。
**拿到这把密钥的人可以直接自签一张 `sub=admin` 的令牌，不需要口令。**

- 仓库示例值（如 `dev-secret-key-for-development` 一对）、`CHANGE_ME…` 占位符、短于 32 位的值都不能用于上线。
- 两把必须**各自随机**、互不相同（refresh 与 access 共用一把等于 refresh 令牌没有独立吊销能力）。
- 没设或设成空串 = 每个进程启动时现场随机（安全，代价是重启后全员重新登录）；要稳定的登录态就显式设置。
- 安装脚本（`docker/install.sh`、`install_i18n.sh`、`wrtinstall.sh`）会为新部署随机生成这两把写进 `.env`，**已有值一律不覆盖**。
  Compose 文件需要把这两项透传进容器（本仓库 `docker/` 目录下的 compose 已透传；从别处下载的 compose 不一定有，安装脚本会告警）。
- 启动审计：设成示例值 / 占位符 / 短于 32 位，或两把相同，启动日志会有一条 WARNING（**不拒绝启动**）。告警不响不等于密钥强，请自己检查。

**更换密钥前先保留旧密钥**（存到只有你能读的地方，不要回贴）：旧版 AES 加密的工作区资源载荷是用旧 `NEKRO_JWT_SECRET_KEY` 加密的，
恢复要靠旧密钥（资源页「使用旧密钥恢复」）。旧密钥丢了，这些载荷就恢复不了。然后用 `openssl rand -hex 32` 生成新值。
**换密钥的副作用**：全部已签发令牌当场失效，请在维护窗口进行。

### 1.2 后台 admin 口令（`NEKRO_ADMIN_PASSWORD`）

`admin` 账号的口令就是这个环境变量，没有第二个来源。建议至少 20 位随机口令（`openssl rand -base64 24`）。
启动审计会对 `CHANGE_ME…` 占位符或短于 12 位的值告警（告警线低于建议值是有意的，避免对安装脚本生成的 16 位随机口令误报）。
**轮换这个口令会使旧的 admin 令牌失效**，admin 需要重新登录。没设或为空 = admin 登录不可用。

### 1.3 数据库口令（`NEKRO_POSTGRES_PASSWORD`）

出厂默认值与包名逐字相同，因此任何「扫描日志或备份里有没有口令泄漏」的工具都无法把它与正常文本区分开。
上线前必须改掉，建议长度 ≥ 24。口令仍是出厂默认（含没设置）时，启动日志会有一条 WARNING；同样不拒绝启动。

### 1.4 OneBot 接入令牌与实例认领

每个由控制台创建的实例有自己的接入令牌；部署级 `ONEBOT_ACCESS_TOKEN` 只是没有自己令牌的协议端要出示的兜底值。
把一个账号**认领**（或改绑）进一个有自己令牌的实例后，内置 NapCat 会被自动下发新令牌；**远程协议端**则要由人把该实例的令牌抄进它自己的配置。
账号绑定一变，握手时出示的令牌与该实例要求的不同的连接会被当场断开、重连也会被拒（表现为「认领完成后 Bot 掉线」）。
另一条出路是清空该实例的 `access_token`，退回部署级令牌。

**更换实例接入令牌**：总后台实例详情的「接入令牌」卡片（只有平台方 Super 看得到），换完旧令牌立刻作废、凭旧令牌的连接被断开；
内置 NapCat 自动重新下发配置并重启容器，内置 qbob 自动重新接线，远程协议端要把页面上给出的新令牌抄进自己的配置。
令牌曾对租户可见（例如从租户收回的实例）时，换掉它就能让这个实例重新成为聊天里超级用户命令的可信来源。
部署级 `ONEBOT_ACCESS_TOKEN` 仍然只能改环境变量后重启。

### 1.5 模型组凭据的静态加密密钥（`NEKRO_CREDENTIAL_SECRET_KEY`）

模型组的 `api_key` 在数据库里是密文（`nkenc1:` 前缀）。密钥有两档来源：

| 档位 | 密钥位置 | 说明 |
|---|---|---|
| A（推荐） | 环境变量 `NEKRO_CREDENTIAL_SECRET_KEY` | Docker 部署写进 `docker/.env`（compose 已透传）；裸机写进你自己的 `.env.prod`。不要把它写进仓库里随镜像分发的 `.env.prod` |
| B（默认） | 数据目录下 `credential_secret.key`（应用自动生成） | 权限必须是 `600`；读到权限过宽时启动日志会有 WARNING（POSIX） |

威胁模型要说清楚：数据库备份文件外流、只读拿到数据库连接——**挡得住**；宿主被拿下、整个数据目录连同密钥文件被打包带走——**挡不住**。

- 启动日志里「模型组凭据静态加密」那一句必须与你以为的档位一致；出现「无可用密钥」表示正在**明文**落库，必须先处理。
- **档 B 的密钥文件丢了 = 库里所有模型组的 API Key 都解不开**（读出来是空串并每次报一条 ERROR）。补救只能在后台重填 Key。
  备份时必须**单独**备份密钥材料（与数据库备份分开保管，否则两者放在一起就等于明文），或者直接走档 A。
- 从档 B 换到档 A 是支持的：旧密钥会降级成「只用于解密的历史密钥」，重启时全部重新加密。**确认完成后再删旧密钥文件。**
- 配置文件里的 `MODEL_GROUPS.*.API_KEY` 只有两种合法形态：占位符 `nkmask:1`（该组有 Key，Key 在数据库里）与空串（该组没配 Key），不含明文。
  因此这份 YAML **不是**丢密钥后的恢复来源。
- 启动时若库里存在当前密钥解不开的行，这一次启动**不会**把配置落盘（避免抹掉可能是唯一副本的明文），日志里会点名这些组。
  此时先把原密钥放回去再重启，不要在后台保存模型组。

### 1.6 CC 工作区的模型凭据模式（`NEKRO_CC_CREDENTIAL_MODE`）

- `relay`（默认）：CC 工作区的容器里只有一把只对本工作区有效的中继令牌，CC 调模型时经 NA 的 `/api/cc-relay` 转发，平台方真实的上游 Key 不进容器。要求容器能回连 NA（地址自动推导，推不出来时设 `NEKRO_CC_RELAY_BASE_URL`）。
- `direct`：真实上游 Key 写进容器（`settings.json` 与 `claude` 进程的环境变量），CC 执行的命令能读到它。只在容器确实无法回连 NA 的单租户部署里用。
- **多租户部署不要用 `direct`。** 开着 `direct` 时，租户的工作区（以及绑定里混有租户频道、或曾经归过租户的工作区）拿不到平台方模型，CC 会直接提示改用 `relay`；启动日志里也有一条告警。
- **如果租户工作区曾经在 `direct` 下跑过，平台方应当轮换上游 Key**：那把 Key 可能已经被租户的会话取走，停容器挡不住已经取走的。
- 与模式无关：平台方的工作区资源（SSH 私钥、口令、令牌等）与带环境变量或请求头的全局 MCP 条目，同样不会下发给上面这类工作区；CC 模型预设 `extra_env` 里键名像凭据（含 `TOKEN` / `KEY` / `SECRET` / `PASSWORD`）的项也不会写进它们的配置文件。工作区一旦变成不归平台方，正在跑的容器会被停掉，下次启动就是不带这些凭据的新容器。

### 1.7 邮箱：账户引用密钥与租户自填的邮件服务器（及租户能填的其他出站地址）

- **`email_account_ref.key`**：数据目录下的第二把应用自动生成的密钥文件（第一次算邮箱账户引用时生成，权限 `600`）。它给平台方邮箱的不透明引用（`platform:xxxx`）与发信记录、节日邮件队列里的账户引用算摘要，**不随 JWT 密钥轮换**。备份数据目录时一并备份；丢了不会丢数据，只是这些引用整体变一次（排着队的平台方节日邮件会被跳过）。安装脚本放宽数据目录权限时会跳过它，与 `credential_secret.key` 同一条。
- **租户自填的邮件服务器**（实例自有邮箱选「自定义」，以及从实例转回平台方、主机还没被平台方改过的邮箱）：NA 只解析一次主机名、校验全部结果，再直接连校验过的那个地址。判据与聊天里的下载链接同一份：公网地址，以及 `DOWNLOAD_EXTRA_ALLOWED_NETWORKS` 里的网段（默认是透明代理 Fake-IP 常用的那段基准测试保留地址，RFC 2544）；回环、RFC1918、链路本地、CGNAT、组播、未指定地址一律拒；`ALLOW_PRIVATE_NETWORK_DOWNLOAD` 对它们不管用。
- **开着 Fake-IP / TUN 透明代理的部署，租户自填的出站地址照常能用，内网安全靠代理自己的规则**（0.4.7 定下的口径，与下载一样不额外拦）：代理把域名解析成它地址池里的假地址、再按域名替 NA 连出去，「连到哪里」实际由那个域名的 DNS 决定，控制它的租户能让代理替 NA 连进内网（模型组请求是一次路径固定的 POST，能打到内网里不要登录的 HTTP 接口，报错里也可能带回一部分响应内容）。要拦，就在代理上拦（不让它把这些流量转进内网）；或者把 198.18.0.0/15 从 `DOWNLOAD_EXTRA_ALLOWED_NETWORKS` 里删掉，那样聊天里的下载与租户自填的地址在这类部署上会一起连不上；只担心邮箱的，也可以在系统配置里关掉实例自有邮箱（`EMAIL_INSTANCE_ACCOUNTS_ENABLED`）。有的代理把地址池放在公网段里，从地址上认不出来，删掉那一段也拦不住。
- **租户能填的其他出站地址同样处理**（0.4.7 起）：租户自建模型组的接口地址与代理（对话、嵌入、看图、绘图、转写、拉模型列表、测试连接）、租户填的实例告警 webhook、工作区 MCP 服务器测试。NA 只解析一次、校验全部结果、直连校验过的地址，连上后再核对对端；经 HTTP(S) 代理时让代理 `CONNECT` 校验过的地址；SOCKS 代理对租户出站不支持。平台方自己的模型组与地址不受影响。判据与自填邮箱、聊天里的下载链接同一份，上面那条 Fake-IP 的说明对这些地址一样成立。
  保存或测试时的预检与真正连接用同一份判据，保存时放行、用的时候却连不上的情况不会出现。
- **会嗅探 SNI / Host、按域名重新解析的代理同样不安全**：NA 连的虽是校验过的真实地址，代理却从 TLS 的 SNI 或 HTTP 的 `Host` 里读出域名、自己重新解析后连去别处；NA 连上后核对对端看到的仍是它要连的那个地址，发现不了。不只是 TUN 透明代理：环境变量 `HTTP(S)_PROXY` 指向的显式代理也可能这样做，比如 Clash / mihomo 的混合端口开着 sniffer 的 `parse-pure-ip` 与 `override-destination`，收到 `CONNECT <IP>:443` 也会按 SNI 改写目标。这种部署上，租户能填的出站地址（自填邮箱、模型组、webhook、MCP）与聊天里的下载链接都谈不上安全：要么对 NA 的流量关掉这类改写，要么让 NA 不经这样的代理出站。
- **租户看到的报错不区分「解析不到」与「指向不允许的地址」**（0.4.7 起），也不带解析出的地址：分开说就等于给租户一个查 NA 所在网络 DNS 的工具。具体原因与地址只在 WARNING 日志里（`拒绝租户出站目标`、`拒绝指向非公网地址的…`）。
- **判不出归属的模型组按租户处理**（0.4.7 起）：只有按库重建模型组视图时登记过是平台方、而且从没以租户身份出现过的组，才照平台方的做法连（可以连内网）。启动时建视图那一步就会登记，正常部署感觉不到；如果启动日志里模型组视图没建起来，平台方指向内网的模型组会连不上，先查那一步。
- **聊天里的下载链接**（0.4.7 起）：`download_file`（图片、文件）、`fetch_url_bytes`（表情收集等）、视频分析插件下载视频、OneBot 视频预览取上游，都只解析一次、直连校验过的地址并核对对端，判据不变（默认仍放行 RFC 2544 那段，见 `DOWNLOAD_EXTRA_ALLOWED_NETWORKS`；`ALLOW_PRIVATE_NETWORK_DOWNLOAD` 打开时照原样按主机名连）。给用户 / 模型看的报错同样不分「解析不到」与「被拒」。视频那两处原来不读环境代理，现在与 `download_file` 一样照用。部署方的 HTTP(S) 环境代理改成让代理 `CONNECT` 校验过的地址：`http://` 的链接也走 CONNECT，代理若只许 CONNECT 到 443（Squid 的默认配置就是这样），`http://` 的图片会下载失败，需要放开。SOCKS 环境代理照原来的做法（由代理按域名连，不固定地址）。
- **本机 DNS 与代理看到的不一致的部署：`NEKRO_EGRESS_ENV_PROXY_RESOLVES_HOSTNAME=true`**（0.4.7 起，默认关）。上面两类出站（租户能填的地址、聊天里的下载链接）经环境代理时，默认是 NA 自己解析、再让代理 `CONNECT` 校验过的地址。本机 DNS 被污染或分区解析、靠环境代理出网的部署（例如国内经海外代理访问 googleapis / twimg 一类），NA 解析出的地址是错的（多半仍是公网地址，校验照样通过），代理连过去 TLS 握手失败。打开这个开关后，经**环境代理**的这两类出站改发 `CONNECT <主机名>:<端口>`，由代理解析：NA 仍按自己的解析校验一次，但不再钉地址，代理那边解析到哪里、能不能连进内网，靠代理自己（代理若能连到部署方内网，就得在代理上拦）。租户自己填的代理（模型组上的代理）与直连不受影响。只在确实需要时打开；不要拿 `ALLOW_PRIVATE_NETWORK_DOWNLOAD` 代替它，那会把下载防护整个关掉。
- **这两类出站的主机名解析在自己的线程池里跑**（0.4.7 起，最多 16 个线程）：主机名由外人决定，被黑洞的域名会让解析一直卡到系统解析器超时。卡住的只占这个池子，不拖住别处的 `to_thread` 与平台方的出站；同一主机名同时只查一次，没人等的查询从队列里撤掉。代价是这个池子被占满时，租户与下载的解析要排队，等卡住的那几个超时返回。

### 1.8 实例划转与彻底删除：上一任主人留下的东西

实例划给别的租户（或从租户收回）就是换了主人；实例标识也可以被重新认领，彻底删除之后同一个标识可能落到别的租户手里。上一任主人填的、能拿去用的东西，默认都不跟过去。

**划转**（租户详情 →「实例归属」→ 保存；确认框逐个实例列出各项条数）：

| 东西 | 处理 |
| --- | --- |
| 用户登记的服务器凭据 | 默认删除，取消勾选才跟着实例走 |
| 实例自己填的邮箱（连同收到的信与附件） | 默认删除，取消勾选才跟着实例走 |
| 插件设置：实例上与它各个频道上的插件开关、实例单独填的插件配置（API Key 之类） | 默认删除，取消勾选才跟着实例走 |
| 配置覆盖：实例与它各个频道单独改过的配置（告警 Webhook、选用的模型组、提示词、输出过滤词表等） | 默认删除，取消勾选才跟着实例走 |
| 记忆、世界书、好感、收集的表情、用户邮件偏好 | 默认跟着实例走，勾选「一并清空」才删 |
| 旧租户设的频道额度与暂停提示；平台方给这个实例的表情套组分配与点名的邮箱共享；白板只读链接；还没发出的节日邮件 | 每次都清，不受勾选框控制 |

这些都在改归属**之前**处理：删不掉就整次保存失败、归属不变，重试会接着删。插件设置与配置覆盖在改归属**之后**还会再删一遍（两次之间前一个主人的后台页面还能写；这一遍删不掉只记警告）。原样再保存一次（实例集合没变）什么都不删。存量数据里同一个实例标识在两个适配器下各有一个实例、只有一个改归属时，插件的实例级设置是两个共用的，勾着「删除插件设置」会被拒绝——先按启动日志里的告警给其中一个换标识。

**彻底删除实例**：上面这些一律删，插件设置与配置覆盖也在内——删库之前删一次（删不掉就整次删除失败、实例原样留着），删库之后再删一次（前面清理向量、表情、附件哪一步出错都照样做），以后用同一个标识新建的实例从空白开始。由平台方邮箱「转为实例自有」的邮箱，附件目录沿用的是地址名，删的时候只删这个邮箱名下那几封信的附件，目录里别的文件不动（目录删空了才删目录）。实例自己的邮箱在删库之前就断开收信：万一后面删库失败、实例留了下来，这些邮箱要等 NA 重启才重新连上收信。

**新建实例**（总后台新建、认领为新实例、协议端自动登记）：建之前把这个标识上残留的插件设置与配置覆盖清掉、平台方邮箱共享名单里点名这个标识的项摘掉，有残留会在日志里记一条 WARNING。协议端自动登记时清不掉也照样登记（不能挡住消息），日志里记一条 ERROR，这个实例带上「待补扫」标记：认领、并入别的实例、划转之前会再清一遍，还清不掉就拒绝这次操作。

**实例迁移、频道换标识**：插件开关、实例单独填的插件配置与配置覆盖跟着搬到新的实例 / 频道标识下，频道级开关不丢；新标识下已经有的设置保留，不被覆盖。**两个实例归属不同时**（迁移历史、把待认领的协议端并入别的租户的实例），源实例的服务器凭据、插件设置与配置覆盖默认删除，确认框里有个数与勾选框，取消勾选才跟过去。选了删除的那几样一样都不搬：迁移开始前删一次（删不掉就整次不做），搬的过程中源实例上新写的也不会跟过去，搬完再删一遍。源实例的标识在别的适配器下还有一个实例时，勾着「删除插件设置」会被拒绝（同上，实例级插件设置是共用的）。

**实例标识**：新建实例时标识按不分大小写查重（`Bot1` 与 `bot1` 算同一个，大小写不敏感的文件系统上它们的设置目录是同一个）；微信多实例新建时标识只能用字母、数字、下划线和连字符。

插件数据目录、配置覆盖目录、邮箱附件目录里如果有符号链接或目录联接：删除时只删链接本身，不进入它；插件的 `<插件>/`、`instances/` 或配置覆盖所在的目录本身是链接时，删除与划转会报错停下，需要人工处理。

存量数据里如果有两个适配器用着同一个实例标识（启动日志会告警），它们共用一份实例级插件设置，删、搬的时候一起处理；这种情况请按告警里的说明给其中一个换标识。

## 2. 备份与日志

### 2.1 备份里不含 `.env*`

备份包不应包含 `.env`、`.env.*` 等凭据文件。对着实际产出的备份包检查，应当 0 命中。
密钥材料（见 §1.5）按上面的说明单独保管；数据目录里的 `email_account_ref.key`（见 §1.7）随数据目录一起备份即可。

### 2.2 日志与诊断

- loguru 的 `diagnose` 默认关闭（环境变量 `NEKRO_LOG_DIAGNOSE`）。开启后异常日志会打印每个变量的取值，**可能把凭据写进日志**，生产环境不要开。
  启动日志会有「loguru diagnose 已关闭」或「已开启」一句，出现「已开启」请先处理。
- 访问日志里的 URL query 上的令牌会被遮蔽；同时遮蔽不应把访问日志遮成一片空白。
- 应用日志级别由 `APP_LOG_LEVEL` 控制，默认 INFO。

### 2.3 用量账本的收尾日志

每次正常停机，日志里有一行 `llm usage ledger flushed`（INFO 级，带 `dropped=` 与 `failed=` 计数）。正常停机应当每次都有这一行且两个计数为 0；
非 0 会另有一条 WARNING 说明丢弃了多少条。整行缺失说明进程不是正常停的（例如被 `kill -9`），队列里最后几条记账会丢。

### 2.4 上传图片保留期（`UPLOADS_IMAGE_RETENTION_DAYS`）

聊天里收到和发出的图片都落在 `DATA_DIR/uploads/` 下，NA 默认永远不删。群多、图多的部署每天能多出几个 GB，根盘迟早写满。
系统配置「基础设置 → 上传图片保留天数」可以让 NA 每天清一次过期图片。

- **默认 0 = 关**，与上游一致：不扫描、不删、不写日志。只有平台方能改：租户在配置页看不到这一项，实例、频道的覆盖配置里也没有它。
- **怎么开**：在系统配置里填一个正整数 N 并保存，不用重启。NA 每 10 分钟看一眼这个值，看到打开后开始第一轮；之后每天一轮。
  进程每次启动后等 5 分钟先跑一轮。改回 0 立即停：正在跑的那一轮在下一批之前停下。
- **删什么**：`uploads/` 下修改时间早于 N 天的图片，按扩展名认：`jpg` `jpeg` `jfif` `png` `gif` `webp` `bmp` `heic` `heif` `avif` `tif` `tiff`，不分大小写。
  视频、语音、文档、压缩包等其它类型一律不动；`uploads/email_attachment/`（邮件附件）整个目录不动。
  同一张图片再次收到或发出时会重新写盘，修改时间跟着刷新，从那天重新算。
- **不越界**：不跟随符号链接（链接本身不删，指向的目录不进）；子目录实际位置不在 `uploads/` 里的整棵跳过并记一条 WARNING。
  `uploads/` 本身放在链接后面没关系，按链接指向的真实目录清。
- **日志**：每轮结束一行 INFO，例如 `上传图片保留期清理完成（保留 3 天）：删除 1234 个图片、567890 字节（0.5 MB），失败 0 个，耗时 2.1 秒`，不打印文件名。
  单个文件删不掉记一条 WARNING（每轮最多 20 条，再多只计数），接着删别的。
- **开了以后的影响**（打开前请确认能接受）：
  - 控制台聊天记录和网页会话里，超过 N 天的图片显示不出来（取件返回 404），消息文字照常显示；
  - 沙盒里 `/app/uploads` 下的旧图片读不到，Agent 写的代码要再处理旧图片会报找不到文件；
  - Agent 拼上下文时历史图片文件不在就跳过（原来就这样处理），聊天上下文的时间窗（`AI_CHAT_CONTEXT_EXPIRE_SECONDS`，默认 30 分钟）比 N 天短，看图就不受影响；
  - 不受影响：表情包收藏（收藏时已复制到插件自己的数据目录）、知识库、记忆、人设头像、邮件附件、视频与其它文件。
- **怎么选 N**：先看 `uploads/` 每天的增量（`du -sh` 隔天各看一次），按磁盘余量反推；想保留控制台里能翻到的图片就选大一点。

## 3. 镜像与部署

### 3.1 镜像

| 镜像 | 用途 |
|---|---|
| `ghcr.io/akiyo-dayo/nekro-agent-byakiyo:<版本号>` / `:latest` / `:preview` | 主应用 |
| `ghcr.io/akiyo-dayo/nekro-agent-byakiyo-sandbox:<版本号>` / `:latest` / `:preview` | 沙盒（`SANDBOX_IMAGE_NAME` 的默认值；安装脚本会 `docker pull` 它） |

沙盒容器由应用通过 Docker API 创建，缺镜像时自动拉取**不带任何凭据**，所以沙盒镜像必须先在宿主上手动拉取，之后更新镜像也要手动 `docker pull`。

`SANDBOX_IMAGE_NAME` 的默认值只对新生成的配置生效；配置文件里已经写着旧镜像名的存量部署要自己改（配置文件或 Web 界面）。

### 3.2 `docker.sock` 硬化

默认部署把 Docker 套接字交给应用。需要更严的边界时使用 `docker/docker-compose-x-hardened.yml`，原理、能挡与不能挡的攻击面见 [`docker-guard.md`](./docker-guard.md)。
它**不是完整的沙箱**，开启前请先读完那份说明。

### 3.3 同宿主多部署

同一台机器上跑多套部署需要区分 `INSTANCE_NAME`、端口与数据目录，见 [`multi-deploy-same-host.md`](./multi-deploy-same-host.md)。

### 3.4 OneBot：同账号其他程序的消息与视频

**看见其他框架发的消息。** NA 和别的框架（如 Yunzai）接在同一个协议端账号上时，要让 NA 看到对方发的消息，协议端必须上报自身消息。

| 协议端 | 要做什么 |
|---|---|
| 内置 NapCat | 托管连接已默认打开 `reportSelfMessage`。`resync_network_config` 在**创建或重启容器**时把它写进配置，所以升级后要**重启一次 NapCat 容器**。只重启 NA 不会改配置。用户自建的连接不动。 |
| 远程协议端 | NA 碰不到它的配置，要自己在 NapCat WebUI 的网络配置里，给连到 NA 的那条连接打开“上报自身消息”。其他实现按各自文档开启，事件是 OneBot 的 `post_type=message_sent`。 |

没有打开时什么也不会坏，只是这些消息继续不可见，不报错。

这类消息只记录，发送者显示为 `账号昵称（同账号其他程序）`。它们不执行命令，不调 `on_user_message`，不计好感，不占配额，也不会被随机搭话和关键词触发，所以两个框架不会互相触发。关闭：`ONEBOT_RECORD_SELF_SENT=false`，可以按频道覆盖。

NA 自己发的消息也会回传，按 `message_id` 去掉。AI 语音（`send_group_ai_record`）NapCat 固定回 `message_id: 0`，按频道留一张票，30 秒内只认领这个群里下一条**带语音段**的回传；别的程序发的文字不会被它吞掉。语音回传先认领语音专用的票，再看普通的无编号票。同一群里别的程序恰好在这 30 秒里也发了语音、且先到时，被认领的是那一条：它不进记录，NA 自己的语音回传反而记成外部消息。如果一次发送超时但实际发出去了，这条消息会被当成外部消息记录：NA 这边发送失败没有记录，记成外部消息至少不会丢，也不会触发。

**视频。** 视频消息始终进聊天记录，不依赖视频分析插件。插件关着时 AI 知道有视频，但看不到内容，会如实告诉用户。占位文字 `[Video: message:<编号>]` 只在落库时补进文本，不参与关键词触发、`AI_CHAT_IGNORE_REGEX` 禁词和伪造消息检查：配了 `message`、`Video` 这类关键词或禁词，不会因为一条视频被触发或丢掉。

WebUI 里点开视频才加载，每次都向协议端要最新链接，再由 NA 转发给浏览器。链接带 `rkey`，不落盘、不缓存、不写日志；播放地址是短时效签名（有效期 10 到 20 分钟），绑定消息、频道和用户，过期后页面自动换新地址接着放。

播放地址在有效期内每次请求都会复核一遍：用户被封禁、降到 Admin 以下、移出租户，或者改过口令（自助改密、管理员重置、admin 轮换 `NEKRO_ADMIN_PASSWORD`），已经发出去的地址立刻失效，与登录令牌同一套口令世代。地址带两段签名：第一段不查库就能验，伪造的地址碰不到数据库；第二段签进口令世代，取到用户之后再验。

| 现象 | 原因 |
|---|---|
| “协议端不在线” | 该实例的协议端没连上 NA |
| “视频链接已失效” | QQ 链接过期且 `get_file` 也取不到，或协议端重启后不再认识这个消息编号。NapCat 的编号映射只在进程内存里 |
| “这个视频已被撤回” | 撤回的视频不再提供播放，签发过的地址也立刻失效 |
| “视频暂时无法播放” | 同时在转发的视频到了上限（见下），关掉几个再点重试 |
| “浏览器无法播放” | 编码浏览器不支持，比如 H.265 |

转发的上限：

| 项 | 值 | 说明 |
|---|---|---|
| 单次大小 | 512 MB | 与视频插件大小限额的硬上限相同 |
| 单次时长 | 30 分钟 | 连同读上游、等浏览器一起算；到点断开，浏览器继续播放时带 Range 重新请求 |
| 浏览器不收数据 | 60 秒 | 暂停后浏览器停读，连接挂在发送上；60 秒后断开，释放上游连接和名额 |
| 同时转发 | 每个用户 6 条；每个租户最多 8 条，其中 2 条保底；全部 32 条，最后 8 条只给保底与平台方 | 含点开时的探测。每条占一条上游连接和一次 `get_msg`。每用户 6：浏览器对同一主机最多 6 条 HTTP/1.1 连接，正常播放碰不到。租户保底 2 条＝一个视频播放加拖动时重叠的那一次请求；保底之外的名额只在全局还剩 8 条以上时发，所以不管多少个租户同时撑满，租户合计最多占 24 条，剩下 8 条够 4 个别的租户各看一个视频，或者留给平台方。平台方账号只受每用户与全局上限约束。超了返回 429 |
| 上游不认 Range 时能拖到的位置 | 前 64 MB | NA 要先读掉起点之前的字节再丢弃；更远的位置直接回 416，不替请求方下载。上游认 Range 时不受限 |

断开（发送超时、到时长上限、上游没给长度而视频超过 512 MB）时 NA 不发结束帧，由服务器直接断连接，浏览器看到的是一次中断而不是“视频到此为止”。为此计时中间件改成了纯 ASGI：以前的 `BaseHTTPMiddleware` 会替内层补结束帧，上游是分块传输时截短的视频会被当成完整的。NA 前面的反向代理在上游中断时会不会替它补全分块响应，没有验证过。服务器日志里每次断开会有一条 “ASGI callable returned without completing response” 之类的记录，这是预期的。

链接走与图片下载相同的出站校验（每一跳都校验，连上之后再按实际对端判一次，挡 DNS 重绑定），只配了 `HTTP_PROXY` 才能出网的部署取不到视频。

**本机文件后备只对内置 NapCat 生效。** 协议端拿不到在线链接时只会给出它自己机器上的路径。实例是总后台创建的内置 NapCat（`provider=builtin_napcat`）时，NA 把容器里的 `/app/.config/QQ/...` 换算到 `napcat_data/<实例>/QQ/...` 去读；其余情况一律不读本机文件，哪怕同名位置上真有文件：

- 远程协议端，包括用 `docker-compose-x-napcat.yml` 起的那个 NapCat（它在 NA 看来是一个远程连接，数据目录是单实例年代的 `napcat_data/QQ`）；
- 有实例键时不回落 `napcat_data/QQ`；会话标识里没有实例键的老频道也不读；已删除（软删）的实例不读；
- 实例的 `napcat_data/<实例>/QQ` 本身不能是符号链接：`resolve()` 之后必须正好落在 `DATA_DIR/napcat_data/<实例>/QQ`（`DATA_DIR` 自己可以是链接）。内置 NapCat 的容器能写这个目录，把它换成指向 `/` 的链接就能扩大界线；
- 路径里任何一段带反斜杠、冒号或 NUL 都直接拒绝，不做任何文件查找。NA 原生跑在 Windows 上时，这种段会把路径换成另一块盘或 `\\主机\共享`，查找本身就会向那台主机发起 SMB 连接；
- 只读视频后缀（`.mp4` `.m4v` `.webm` `.mov` `.mkv`），按 `resolve()` 后的真实位置判断，必须仍在该实例的 QQ 目录里；打开时不跟随符号链接，打开后按已打开的文件复核一次真实路径（Linux 读 `/proc/self/fd`，Windows 用 `GetFinalPathNameByHandleW`，macOS 用 `F_GETPATH`，都取不到时核对路径上的文件与已打开的是同一个，不跟随链接）。按平台选，不看 `/proc` 存不存在：Windows 上 `/proc/self/fd/N` 会落到盘根目录，那里普通用户就能建目录。视频插件复制本机文件用的是同一段代码；本机文件被拒时插件与 WebUI 一样换协议端给的下一个地址。

**`get_file` 的结果要和记录对得上才用。** NapCat 的 `get_file` 按文件名取件：先查以文件名为键的内存缓存（后到的同名文件会覆盖），查不到时在文件助手里全局按名搜索、取第一条（NapCat `v4.18.42` 源码 `action/file/GetFile.ts`），所以可能拿到别的会话里的同名文件。NA 只用文件名和大小都与聊天记录一致的结果；记录里缺这两项时不调 `get_file`。用的不是 NapCat 的协议端，`get_file` 不回 `file_name` / `file_size` 时这一级后备不可用。

### 3.5 CC 工作区容器

**只支持单进程部署。** 工作区容器的启动、重启、重建、停止靠进程内的锁加数据库里的过渡状态（`transitioning`）串行。起多个 worker（`uvicorn --workers N`、多副本）时锁各管各的，数据库里的比较替换挡得住同时改状态，挡不住另一个进程直接操作 Docker——别这样部署。进程在启停中途退出留下的 `transitioning`，下次 NA 启动时核对；超过 10 分钟没动的，停止与删除也会接管。

**换版之后的第一次启动。** NA 启动时会：删掉库里没记的 CC 容器（升级前每次启动都换新名字，停着的旧容器一直堆着；并发启动、健康检查超时留下的也在其中）；逐个核对库里记着的容器的挂载，来源不是这个工作区目录 / 它的 CC home（见下一条）/ 宿主的 `/etc/localtime`（只读），或者有预期之外的挂载目标，就停掉它、把工作区标成 failed，要求重建。没有 `/etc/localtime` 那一条不算不一致。Docker Desktop 会把挂载来源改写成 `/run/desktop/mnt/host/...`，在那上面跑的开发部署会被判成不一致，用「启动」（新建容器）即可。

**CC home 的位置。** 挂进容器当 `~/.claude` 的目录（会话历史、技能、`.claude.json`、SSH 网关钥匙）在 `{数据目录}/workspaces/.nk-homes/<id>/claude`，不在工作区目录里（0.4.7 之前是 `{数据目录}/workspaces/<id>/.claude_home`，同时也在容器读写挂载的 `/workspace` 里，容器能把它换成指向宿主别处的链接）。`.nk-homes` 与 `<id>` 两级是 0700、属 root，只有 `claude` 本身是 0777。NA 在 home 里建的、写的东西（home 本身、`settings.json`、`skills/` 与里面的技能、SSH 网关私钥）都交给容器里跑 CC 的用户（镜像的 `appuser`，uid / gid 1000），因为镜像入口脚本只 `chown` 工作区、碰不到 `~/.claude`；`nk-ssh` 目录与两个配置文件留给 root，私钥照旧 0600。NA 不是 root（也不是 uid 1000）时改不了属主，第一次往 home 里写东西时记一条 WARNING（只记一次），这时容器里的 CC 可能写不进 `skills/`。老工作区在下一次「启动」或「重建」时自动迁过去（同一文件系统上的一次改名，不复制）；「重启」沿用容器原来的挂载，不迁。迁不动（例如工作区目录单独挂在另一个文件系统上）时照旧按旧位置启动并记一条 ERROR。NA 每次启动用一条 WARNING 列出还在旧位置的工作区。已经迁过、工作区目录里又出现一份 `.claude_home`（没跑回滚脚本就退回旧版本、又升级回来：旧版本会往里写设置和网关钥匙，`direct` 模式下设置里是平台 Key）时，下一次启动、重建、重启（容器停着的那会儿）或 NA 启动复核会把它整个挪到 `.nk-homes/<id>/legacy-<时间>`（0700，不挂进任何容器），WARNING 里写着路径，确认没用了可以删；挪不动时删掉里面 NA 写过的 `settings.json` 与 `nk-ssh`，记 ERROR。删工作区时 home 一起删（工作区目录照旧保留）；新建工作区时如果同一个编号还留着 home（数据库重置过），先清掉，清不掉就不建。要退回 0.4.7 之前的版本：停掉 NA 与所有 CC 工作区容器，用 root 跑 `sudo python3 scripts/workspace_homes_rollback.py --data-dir <数据目录>` 看要搬哪些、加 `--apply` 搬回旧位置（NA 进程或读写挂着数据目录的容器还在跑时它拒绝；别的部署的容器、只读挂 `uploads` 的 NapCat 不算；没有 `/proc` 或 `docker` 命令时确认停干净之后加 `--skip-process-check` / `--skip-docker-check`；搬回去的 home 照上面的口径交给 uid 1000），换回旧版本后对每个 CC 工作区点一次「重建」。

**升级前建的容器缺两项加固。** 新建的容器带 `CapDrop: MKNOD` 与 `no-new-privileges`；升级前建的没有，重启补不上，日志里会提示「建议重建容器」。不拒绝重启，按需逐个重建。

**别的容器以读写方式挂着数据目录。** 启动 / 重启工作区容器前，NA 会检查有没有在跑的容器以读写方式挂着这个工作区目录、它的 CC home，或者它们的任何一级上级（`.nk-homes`、数据目录、`/` 等）；有就拒绝启动、记 ERROR 并写明是哪个容器。NA 自己放行。只读挂载不算。自己加的备份 / 文件管理之类的边车容器请改成只读挂载，或者只挂它需要的子目录。

**NapCat 只挂 `uploads`。** NA 交给 NapCat 发送的文件都先放进 `{数据目录}/uploads`，所以控制台建的 NapCat 与随项目发布的 compose 文件都只把它只读挂到容器里的 `/app/nekro_agent_data/uploads`（配置项「协议端挂载 NA 数据目录」的默认值 `/app/nekro_agent_data` 不变）。升级前建的 NapCat 还读写挂着整个数据目录：0.4.7 照样放行，但每次启动 CC 工作区记一条 WARNING，下一个版本起按上一条拒绝。控制台托管的在控制台里删掉容器再创建一次（QQ 登录态在 `napcat_data/<实例>` 里，保留）；compose 部署把 NapCat 那一段的数据目录挂载换成新 compose 文件里的写法后 `docker compose up -d`。插件如果把 `uploads` 以外的路径直接交给 NapCat 发送，换挂法之后会失败——NA 自己的发送路径都会先复制进 `uploads`。

## 4. 运维通道：`/na_ops` 与给 Agent 调用的运维工具

两者都是平台方专属，总开关 `OPS_AGENT_TOOLS_ENABLED` 默认关。运维人员名单、运维群、私聊开关都在系统设置里，租户看不到。写操作直接执行，不在聊天里二次确认；每次执行后宿主在频道里发一条固定格式的回执（带记录号），全部调用记在运维审计里（后台「运维审计」页、`/na_ops audit`），保留 365 天。

**运维群只放运维人员。** 群里每一句话都会进 Bot 的上下文。下面几种情况，这一轮里 Bot 仍可以查，但**不会执行任何写操作**，会告诉你改到私聊里或回后台操作：

- 上下文里有不在运维人员名单上的人的发言；
- 上下文里有推送进来的外部内容（定时提醒、CC 结果、GitHub 事件、邮件通知……）；
- 上下文里有同一账号由其他程序发出的消息；
- 这一轮里 Bot 读过外部内容（错误日志、实例的最近错误、网页、其他插件的结果）——这种情况运维人员再说一句，下一轮就能执行。

前三种要等那些消息移出上下文才恢复，所以运维群最好是只有运维人员、平时安静的群。

**这道判断看不到的地方。** 长期记忆、世界书、插件挂在提示词上的内容（比如状态笔记）不在聊天记录里，Bot 照样会读到。不要给运维群开长期记忆、绑世界书，也不要在运维群里让 Bot 记笔记；这些内容如果来自名单外的人，可能诱导 Bot 去执行一次写操作。兜底是只放可撤回的操作、回执与审计。

## 5. 世界书预算（0.4.7 起按 token 计）

每轮注入多少世界书由两项决定（系统配置 → 世界书，实例、频道可以覆盖，租户只能往下调）：

- **占上下文的百分比**（`WORLDBOOK_BUDGET_PERCENT`，1 ~ 100，默认 25）：每轮最多占「主模型组的上下文长度 − 4096」的百分之几；
- **token 上限**（`WORLDBOOK_BUDGET_CAP_TOKENS`，0 ~ 65536）：取两者中较小的一个。0 表示不另设上限、只按百分比算。

不管这两项怎么填，**每轮预算最多 65536 token**（硬上限）：模型组的上下文长度最多能填一千万，没有硬上限的话，上限 0、25% 就是每轮两百多万 token。

上下文长度取频道生效的主模型组上填的「上下文长度」，**没填按 32768 算**（25% 约 7168 token、九千来字）。不按模型名猜：中转站的模型名千奇百怪，猜成一百万的上下文，25% 就是每轮 26 万 token。上下文长度填了、但不超过 4096（回复预留）时，世界书每轮只剩 1 token、注入不了任何条目：不拦，模型组页面上会提示，保存与启动时日志里各记一条 WARNING。

**建议平台方在全局给一个 token 上限**（比如 8000 ~ 16000）。之后有人给模型组填了很大的上下文，世界书也不会一下子把费用放大十倍；租户只能在这个上限以下调，不能改成 0（「不另设上限」）。

token 按 tiktoken 的 `o200k_base` 在本地数（编码文件随镜像发布，不联网），再乘模型家族的分词系数（DeepSeek 0.80、Gemini 0.89、Qwen 0.90、Claude 1.29 等；模型组上可以填自己的系数）。系数是在中文设定正文上量的，英文、代码会有一两成出入。

**从 0.4.6 升级**：首次启动时把旧的「每轮正文字数上限」（`WORLDBOOK_MAX_CHARS`）自动换算，已经在用世界书的部署每轮注入多少基本不变：

- 全局写「占上下文的百分比 = 100」，预算由上限决定；
- 每一层设过的字数按 1 字 = 0.8 token 换成同一层的 token 上限（默认 3000 字 → 2400 token、6000 → 4800）；
- 设成 0 字（原义「不注入」）的层改成同一层的 token 上限 1：1 token 实际上放不进任何条目，租户也抬不上去（新上限里 0 是「不另设上限」，意思相反，所以不能照抄 0）；全局设成 0 字时全局上限也是 1；
- 书级预算同样 × 0.8（数据库迁移做）。

某一层的覆盖文件写不回去时，只跳过这一层（别的层照常换算），迁移提示里点名这一层：它原来的字数上限没有换成 token 上限，现在继承上一层，需要到这一层的配置里手工设。

因为计数时还乘分词系数，迁移后能放下的字数随模型略有出入：DeepSeek 多放约两成，Claude 少放约两成。想换成 SillyTavern 的默认玩法，把全局的百分比改成 25、上限改成 0（不另设上限，仍不超过 65536），再给模型组填上真实的上下文长度。迁移逐层写进日志，平台方在系统配置页顶部能看到一次性提示，点「知道了」后不再显示；提示里有各实例、频道的会话标识，只给平台方看。旧配置项保留一个版本只为让旧配置文件照常加载，不再生效，0.4.8 删除。

## 6. 嵌入（向量化）长期失败的提醒（0.4.7 起）

记忆沉淀、召回、近重复检查、知识库、表情包插件的嵌入调用失败时，各处都只记一条 WARNING、照常往下走（记忆照存但没有向量，召回退回空，知识库退回关键词），所以 Key 失效这类问题以前要很久才会被发现。现在按模型组记成败：

- **鉴权、额度、地址或模型名不对**（401 / 403、402 / 429、404 等其余 4xx）：连续失败 3 次、且第一次到最近一次至少隔一分钟，就判长期失败；
- **网络、上游 5xx、回包形态不对**：从第一次失败起 30 分钟仍没有成功过一次才判；
- **跟这一条输入有关的拒绝**（400 / 413 / 422：单条太长、格式不对、被内容审核拦下）：不算失败，也不打断正在累计的失败，只在状态接口里记次数（`input_rejections`）。个别兼容接口把模型名写错也回 400，这种情况不会提醒；这个次数一直在涨就该查模型名。

判成长期失败时日志里记一条 ERROR，并通过现有的通知渠道提醒一次：模型组归平台方就发平台方的邮箱、平台方的告警 Webhook 与运维频道；归某个租户就只发这个租户自己实例层上配的告警 Webhook。归属在判成长期失败的那一刻查定；那时库里已经查不到这个模型组（被删了）就谁都不发，只在日志里记一条 WARNING。之后再失败不再重复记、不再重复发；下一次成功时记一条 INFO（「嵌入调用已恢复」）。同一个模型组 6 小时内只提醒一次。

记忆页顶部会出现一条红色提示，写着错误类别、从什么时候开始失败、最近一次失败与最近一次成功的时间（接口 `GET /api/console/health/embedding`，租户只看得到归自己的模型组）。状态只在进程内存里：重启后如果还在失败，会重新判、再提醒一次。提示与日志里只有类别和 HTTP 状态码，不带上游返回的原文（原文里常回显 Key）。

修好 Key、额度或网络以后不用重启，下一次嵌入成功就自动恢复。恢复前沉淀的那些记忆仍然没有向量：平台方在提醒正文与记忆页上能看到「有多少段有效的记忆缺向量」（不数正文全是空白的段落，最多一分钟更新一次；不在失败时记忆页显示一条蓝条；没配记忆嵌入模型组时不显示），可用超级用户命令 `memory_backfill_vectors` 补齐。
